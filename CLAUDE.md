# TRAINING — SIMA TRAINING Platform

## Qué es esto

MVP de alta fidelidad para validar la plataforma **SIMA TRAINING** de **Ingeniería Sima** ante clientes de la industria Oil & Gas. Nació como demo navegable solo-frontend (datos mockeados) y desde el **Sprint 1** tiene un **backend real** (NestJS + PostgreSQL): el ABM de Usuarios del backoffice ya persiste contra base de datos. La app tablet sigue mockeada por ahora.

**SIMA CHECK** (capacitaciones y evaluaciones industriales) es el primer producto integrado en la plataforma. La arquitectura está preparada para incorporar productos futuros (SIMA INSPECTIONS, SIMA AUDITS, etc.) sin reorganizaciones.

## Stack técnico

**Frontends** (`sima-training-backoffice`, `sima-check-app`):
- **Vite + React** (template react)
- **Tailwind CSS v3** + PostCSS + Autoprefixer
- Sin router (navegación con `useState`)

**Backend** (`sima-training-api`):
- **NestJS 11** + TypeScript (monolito modular por dominio)
- **PostgreSQL 16** (local vía Docker Compose)
- **Prisma 6** (ORM + migraciones)
- **JWT** para auth básica (sin roles todavía)

> El backoffice ya consume la API real (ver `src/core/api/`) en **Usuarios, Puestos, Centros de Costo, Módulos, Preguntas, Reglas de asignación y Asignaciones**. Siguen mockeadas **Dashboard, Clientes y casi todo el Resumen de SIMA CHECK**; se migran ABM por ABM en sprints siguientes. La app tablet (`sima-check-app`) todavía no está conectada.

## Cómo correr

Detalle completo del backend en [`sima-training-api/README.md`](sima-training-api/README.md).

```bash
# 1. Backend (requiere Docker Desktop corriendo)
cd TRAINING/sima-training-api
npm install
cp .env.example .env
docker compose up -d db          # PostgreSQL local
npx prisma migrate dev           # crea las tablas
npx prisma db seed               # organización interna + módulos base
npm run start:dev                # → http://localhost:3000

# 2. Backoffice
cd TRAINING/sima-training-backoffice
npm install
cp .env.example .env             # VITE_API_URL apunta al backend local
npm run dev                      # → http://localhost:5173

# 3. App tablet (mockeada, sin backend aún)
cd TRAINING/sima-check-app
npm install
npm run dev                      # → http://localhost:5174
```

### Entidades reales (Prisma — `prisma/schema.prisma`)

| Entidad | Campos clave |
|---|---|
| `Usuario` | `id, nombre, apellido, dni` (único), `email?`, `datos` (jsonb) + trazabilidad + `deletedAt` (soft-delete). **Identidad pura**: no tiene rol, ni organización, ni clasificación (ver `Vinculacion`) |
| `Vinculacion` | `id, usuarioId` (**único** — una vinculación por usuario), `organizacionId` (FK), `rol` (ADMINISTRADOR/COORDINADOR/**AUDITOR**/ALUMNO), `activa` + trazabilidad + `deletedAt`. Es donde viven organización y rol desde el modelo de vinculación |
| `VinculacionPuestoCentro` | PK `[vinculacionId, puestoId, centroCostoId]` (los tres NOT NULL), `principal` (solo display), `activo` (baja lógica). Un **par** (puesto, centro de costo) que la persona ejerce. Una vinculación puede tener **cero, uno o varios** pares |
| `Puesto` / `CentroCosto` | `id (uuid), nombre` (único), `activo` + trazabilidad — catálogos de nómina |
| `Organizacion` | `id, nombre, tipo` (CLIENTE/SUBCONTRATISTA/**INTERNA**), `organizacionPadreId` (FK self-referencial), `activa` + trazabilidad |
| `Pregunta` | `id (uuid), texto, tipo` (VERDADERO_FALSO/OPCION_MULTIPLE/OPCIONES_IMAGEN/TEXTO_LIBRE), `opciones?` (jsonb: array de strings — texto en OPCION_MULTIPLE, **claves de storage** en OPCIONES_IMAGEN), `respuestaCorrecta?` (el string exacto de una de las opciones; el backend lo valida), `imagen?, puntajeMax?, activa` + trazabilidad. Única: se comparte entre módulos, nunca se duplica. `imagen` es la **imagen del enunciado**: guarda una **clave opaca** de storage (`preguntas/<uuid>.png`, se sirve bajo `/uploads`) o una ruta legacy relativa a `public/` si vino del import de Excel. Se setea solo al crear y es **inmutable** (ver Sprint 4). **Clasificación (Sprint 6)**: `baseConocimientoId?`, `nivelId?` y `fuente?` — nullable en base de datos pero obligatoria la base en el formulario de alta (ver Sprint 6) |
| `BaseConocimiento` | `id (uuid), nombre` (único), `codigo?` (único), `descripcion?` (qué entra y qué no), `fuente?` (de qué manual sale el temario **hoy**), `color?, orden?, activa` + trazabilidad. El **tema** de una pregunta. **No se versiona**: es taxonomía, no contenido (ver Sprint 6) |
| `NivelBase` | `id (uuid), baseConocimientoId, nombre, orden` + trazabilidad. La escala **ordinal** de dificultad de una base. Es tabla y no enum porque **la escala es por base**: una puede tener 3 niveles y otra 5. Únicos `[base, nombre]`, `[base, orden]` y `[id, base]` — este último no es unicidad de negocio, habilita la FK compuesta de `Pregunta` |
| `Modulo` | `id (uuid), nombre, descripcion?` + trazabilidad. Contenedor estable; el contenido real vive en `ModuloVersion` |
| `ModuloVersion` | `id (uuid), moduloId, numeroVersion` (contador interno monotónico), `estado` (BORRADOR/ACTIVO/ARCHIVADO), `anio?/mayor?/menor?` (número público `AÑO.MAYOR.MENOR`, se asigna al Activar), `activadaEn?` (timestamp de publicación), `esNuevaLinea?` (elección guardada en el borrador: true = sube MAYOR, false = sube MENOR) + trazabilidad. Editar un módulo activo crea una versión nueva (borrador); al activarla la anterior queda `ARCHIVADO` e inmutable |
| `ModuloVersionPregunta` | Pivot `ModuloVersion` ↔ `Pregunta`. PK `[moduloVersionId, preguntaId]`, `orden`, `obligatoria`, `activa` (baja lógica **por módulo**) y **`origen`** (`CRITERIO`/`MANUAL`, default MANUAL). El `origen` es lo que permite que la resolución de criterios sepa qué filas le pertenecen: crea y borra sólo las `CRITERIO` y **nunca toca las `MANUAL`** (ver Sprint 7) |
| `ModuloVersionCriterio` | `id (uuid), moduloVersionId, baseConocimientoId` (**NOT NULL**), `nivelId?` (null = cualquier nivel de esa base) + trazabilidad. **Qué evalúa** una versión, declarado por tema en vez de enumerando preguntas. Una versión puede declarar varios niveles de la misma base (son criterios distintos). **No guarda cuántas preguntas sortear** — ver Sprint 7. FK compuesta `(nivelId, baseConocimientoId)` → `NivelBase(id, baseConocimientoId)`, igual que `Pregunta`; unicidad con `@@unique` **más** un índice parcial `WHERE nivel_id IS NULL` |
| `ReglaAsignacion` | `id (uuid), puestoId?, centroCostoId, moduloId` (`puestoId` nullable), `activo`, `deletedAt` + trazabilidad. **Dos alcances que conviven**: con `puestoId` es una regla por **par exacto** (puesto, centro de costo); con `puestoId` en **null** es una regla de **centro de costo**, que aplica a todos los puestos de ese centro. Un soldador de Taller alcanzado por las dos recibe los dos módulos — `recalcular()` los unifica en un único `Set` de módulos requeridos, nunca duplica la `Asignacion`. Apunta a `Modulo` (el contenedor), no a una `ModuloVersion` — la obligación es "este módulo", la versión concreta se resuelve al rendir. **Dos ejes de baja independientes**: `activo` es la pausa reversible (sigue listada y se reactiva), `deletedAt` es la eliminación (deja de listarse y de matchear). Volver a crear el mismo triple **revive la misma fila** en cualquiera de los dos casos, nunca duplica. **La unicidad se cubre con dos índices parciales y ningún `@@unique`** (ver abajo) |
| `Asignacion` | `id (uuid), usuarioId, moduloId, moduloVersionId?` (null hasta rendir), `origen` (AUTOMATICA/MANUAL), `revocadaAt?` + trazabilidad. Obligación concreta de una persona de rendir un módulo. **Nunca se borra, se revoca.** Índice único parcial `WHERE revocada_at IS NULL` → a lo sumo una vigente por (usuario, módulo) |

**Tipo `INTERNA`:** La organización **"Ingeniería SIMA"** usa este tipo. Los usuarios que pertenecen a ella son usuarios internos de SIMA (administradores del sistema); el resto (CLIENTE/SUBCONTRATISTA) son usuarios de clientes.

**Decisión clave — `Usuario` es UNA sola entidad** para cualquier persona (cuenta de sistema y/o persona evaluada). Esto unifica los conceptos `User` y `Employee` que el prototipo modelaba por separado. `rol = ALUMNO` es la persona evaluada (equivalente al `Employee`/"Empleado" del modelo de roles); ADMINISTRADOR/COORDINADOR son las cuentas de sistema del backoffice, y AUDITOR es el rol de las organizaciones CLIENTE. **El rol ya no vive en `Usuario`: vive en `Vinculacion`** (ver abajo).

**Modelo de vinculación (`docs/modelo-vinculacion.md`):** `Usuario` quedó como **identidad pura** (nombre, apellido, DNI, email, `datos`). Todo lo que es pertenencia se movió a `Vinculacion` — **una por usuario**, con **organización y rol** —, y el par **puesto + centro de costo** vive en `VinculacionPuestoCentro`, una fila por par completo (los tres campos de la PK son NOT NULL: nunca un puesto sin centro ni al revés).

- Una persona puede tener **varios pares**, y el mismo puesto en dos centros son **dos pares distintos** ("Soldador en YPF" ≠ "Soldador en PAE"): la capacitación obligatoria depende del par, no de dos listas sueltas.
- **Regla de negocio: el alumno hace los módulos de TODOS sus pares**, no solo del principal.
- **`principal` es solo display** — qué par se muestra en la fila del listado. No interviene en ninguna regla de capacitación. Manejo mínimo a propósito: el primer par que se carga queda principal, y no hay herencia automática si después se desactiva (que se muestre un par inactivo es cosmético, no un bug). Si alguna vez hace falta hacer un swap de principal, va en **dos UPDATEs dentro de una transacción** (bajar el viejo, subir el nuevo): el índice único parcial `UNIQUE (vinculacion_id) WHERE principal AND activo` no es diferible y un `updateMany` único lo viola a mitad de camino.
- Cero pares es una cardinalidad válida (el pivote arranca vacío): el listado **no oculta** a esas personas.

**Clasificación (SIMA/CLIENTE/SUBCONTRATISTA/INVITADO): se disolvió como concepto.** Ya no se persiste en ningún lado — la pertenencia se **deriva** de `Organizacion.tipo` (INTERNA/CLIENTE/SUBCONTRATISTA) más la cadena de `organizacionPadreId` ("para quién trabaja" un subcontratista). `INVITADO` quedó fuera del modelo, a definir cuando se implemente el acceso de única vez.

**Matriz tipo-de-organización ↔ rol:** `INTERNA` → todos (ADMINISTRADOR/COORDINADOR/AUDITOR/ALUMNO) · `CLIENTE` → solo AUDITOR · `SUBCONTRATISTA` → solo ALUMNO. Vive en `src/usuarios/matriz-rol-organizacion.ts` y se valida **en el service** (cruza dos tablas — rol en `Vinculacion`, tipo en `Organizacion` — así que no hay CHECK constraint posible, y tampoco puede ir en el DTO). Corre en el alta/edición manual **y en el import de Excel**, que delega en el mismo `UsuariosService.create` en vez de tener su propia copia.

**Composición por criterio (Sprint 7):** el contenido de una versión se puede armar de dos formas que **conviven**: eligiendo preguntas a mano del banco (pivot `origen: MANUAL`, lo de siempre) o declarando **criterios** (`ModuloVersionCriterio`: base + nivel opcional) que materializan el pool de preguntas que matchean (pivot `origen: CRITERIO`). Es un **snapshot**, no una receta viva: el pool se materializa al guardar los criterios sobre un BORRADOR y `activar()` lo congela sin volver a resolver. Detalle completo en Sprint 7, más abajo.

**Banco de preguntas y módulos versionados (SIMA CHECK):** `Pregunta` es única y reutilizable entre módulos vía el pivot `ModuloVersionPregunta` (N a N). `Modulo` nunca se edita en el lugar: cambiar su contenido crea una `ModuloVersion` nueva y la anterior queda archivada e inmutable — no se pierden versiones viejas. Los tipos de pregunta (`VERDADERO_FALSO`/`OPCION_MULTIPLE`/`OPCIONES_IMAGEN`) mapean 1:1 a los tipos del mock frontend (`truefalse`/`multiple`/`image-options`); `TEXTO_LIBRE` está en el enum para uso futuro, sin implementación todavía.

**Clasificación del banco (Sprint 6):** cada `Pregunta` apunta a una **`BaseConocimiento`** (el tema — "Gestión de residuos") y, opcionalmente, a un **`NivelBase`** de esa base (la dificultad). Reemplaza a la vieja `Etiqueta`, que era un N a N de tags libres y estaba **muerta** (nadie la creaba ni la asignaba); se eliminó del todo en el mismo sprint. Motivación: los módulos reales (`SIMA Básico`/`Intermedio`/`Avanzado`) **codificaban la dificultad en el nombre** y disolvían el tema adentro — los dos ejes estaban colapsados en uno. Detalle completo en Sprint 6, más abajo.

**Baja lógica de preguntas por módulo:** una pregunta **no se edita, se activa/desactiva**. El pivot `ModuloVersionPregunta` tiene un flag `activa` (default `true`) que es la baja lógica **por módulo**: desactivar una pregunta la saca solo de ese módulo (togglea el flag en la versión vigente, in place — no crea versión nueva). Es distinto de `Pregunta.activa`, que es el flag global del banco. `GET /modulos/:id` devuelve todas las preguntas del módulo (activas e inactivas) para poder reactivarlas desde el backoffice.

**Papelera global de preguntas (distinta de la baja por módulo):** `Pregunta.activa` es un segundo flag, independiente del anterior — "enviar a papelera" (`PATCH /preguntas/:id { activa: false }`) saca la pregunta de **todo** el banco y cascadea `activa=false` a **todas** sus filas de `ModuloVersionPregunta` (cualquier módulo donde estuviera). "Recuperar" (`activa: true`) revierte el flag global pero **no** restaura los pivots por módulo — asimetría a propósito, para no adivinar en qué módulos el admin la quiere de vuelta. `GET /preguntas` soporta filtrar por `?activa=`, por `?moduloId=` (repetible, combina como OR entre módulos), y por `?sinAsignar=true` (preguntas sin ninguna asignación vigente, también OR con `moduloId`); cada pregunta devuelta trae `modulos: [{moduloId, moduloNombre, activaEnModulo}]` con sus asignaciones actuales.

**Detección de duplicados/similares (resuelto, en memoria):** `src/import/similitud.ts` normaliza el texto en español (sin acentos/puntuación) y compara por coeficiente de Dice sobre trigramas de caracteres, contra el banco completo y contra las filas del mismo archivo importado. Se eligió esta vía en vez de la extensión `pg_trgm` de Postgres porque el proyecto es local-first sin deploy cloud activo todavía; queda encapsulado en funciones puras, reemplazable el día que el banco crezca lo suficiente como para justificar un índice en base. Solo corre en el preview del import — el alta directa (`POST /preguntas`) no la ejecuta.

**Asignaciones automáticas por par (puesto, centro) → módulo:** `ReglaAsignacion` fija qué módulo es obligatorio, por par exacto o por centro (ver tabla de entidades arriba). `AsignacionesService.recalcular(usuarioId)` es el motor: toma los pares ACTIVOS de la vinculación, arma la unión de módulos requeridos por las reglas vigentes que matchean algún par **más** las reglas de centro de los centros donde tiene algún par activo, y la compara contra las `Asignacion` vigentes actuales — crea las `AUTOMATICA` que faltan y revoca las `AUTOMATICA` que ya no corresponden a ningún par activo. Es síncrono e idempotente, y **nunca toca las `MANUAL`** (las que carga un admin a mano). **Se auto-invoca** desde `UsuariosService` (`recalcularEnTx`, dentro de la misma transacción que cambió los pares) — ya no es solo un endpoint aparte, aunque `POST /asignaciones/recalcular/:usuarioId` se mantiene para recalcular a demanda. Los guards exactos, incluido **qué NO lo dispara**, están más abajo en "Backend (Asignaciones automáticas por par)". El registro de aprobaciones ("ya rindió y aprobó este módulo") todavía no existe como entidad: el hueco está aislado en `AsignacionesService.modulosAprobados()`, que devuelve un Set vacío hasta que la app tablet se conecte y exista el flujo de rendir evaluación.

**Convención: `onDelete` explícito en relaciones Prisma opcionales.** El default de Prisma para una relación `?` es `SetNull` — no siempre es seguro. En `ReglaAsignacion.puesto` (opcional porque `puestoId = null` significa regla de centro) se fuerza `onDelete: Restrict`: con el default, borrar un `Puesto` convertiría en silencio una regla de par en una regla de centro, aplicándola de golpe a todos los puestos de ese centro. Regla general para el schema: toda relación opcional nueva tiene que decidir su `onDelete` a propósito, no heredar el default sin pensarlo — **y verificar el SQL de la migración generada**, porque el `onDelete` efectivo no se lee en el `.prisma` cuando es el default. Acá quedó confirmado: la FK sigue siendo `ON DELETE RESTRICT` y la migración que volvió nullable la columna es una sola línea (`ALTER COLUMN "puesto_id" DROP NOT NULL`), sin tocar el constraint.

**Unicidad de `ReglaAsignacion`: DOS índices parciales y ningún `@@unique`.** La tabla **no declara unicidad en el schema**: las dos que tiene viven sólo en el SQL de la migración `20260729171533_reglas_asignacion_soft_delete`, porque Prisma no expresa `WHERE` en `@@unique`.

```sql
-- (a) reglas CON puesto: en Postgres NULL nunca es igual a NULL, así que este
--     índice no cubre las de centro (cada fila con puesto_id NULL es distinta).
CREATE UNIQUE INDEX "reglas_asignacion_par_modulo_vivas"
  ON "reglas_asignacion"("puesto_id", "centro_costo_id", "modulo_id")
  WHERE "deleted_at" IS NULL;

-- (b) reglas de CENTRO, las que se le escapan al de arriba.
CREATE UNIQUE INDEX "reglas_asignacion_centro_modulo_sin_puesto"
  ON "reglas_asignacion"("centro_costo_id", "modulo_id")
  WHERE "puesto_id" IS NULL AND "deleted_at" IS NULL;
```

Los dos predicados son **ortogonales**: `puesto_id` elige qué alcance gobierna el índice, `deleted_at` elige qué filas están vivas — por eso se combinan en vez de unificarse. Con estos dos ya son cuatro los índices parciales invisibles para Prisma del proyecto (los otros: `Asignacion` con `WHERE revocada_at IS NULL`, y el `principal` de `VinculacionPuestoCentro`), y con el `WHERE nivel_id IS NULL` de `ModuloVersionCriterio` (Sprint 7) son **cinco** — misma advertencia: un `db push` sobre una base limpia los deja afuera. La lista completa y verificada está en `docs/pendientes.md`.

Corolarios en el service: `create()` busca con `findFirst` y `puestoId: dto.puestoId ?? null`, no con `findUnique` (que no puede consultar por NULL). El `?? null` es load-bearing — con `undefined` Prisma dropea la condición y terminaría reactivando cualquier regla de ese centro+módulo. Y busca **primero la viva y sólo después la eliminada**: como los índices sólo prohíben dos *vivas*, una viva y una eliminada del mismo triple pueden coexistir (se llega ahí moviendo una regla viva al módulo de una eliminada, porque la detección de colisión ignora las eliminadas), y una búsqueda sin ordenar podía agarrar la eliminada, revivirla y chocar contra la viva.

Incluye el campo opcional **"Imagen del enunciado"** y, si el tipo es `OPCIONES_IMAGEN`, **4 slots uploader** para las opciones con su selector de correcta por miniatura: en los dos casos el archivo se queda en el browser con preview (`URL.createObjectURL`) y se sube recién al confirmar, así quitarlo/cambiarlo antes de crear es estado local y abrir y cerrar el modal no deja huérfanos — ver Sprint 4) y **"Importar Excel"** (`ImportPreguntasModal`: preview con checkbox por fila, badge nueva/parecida-con-%/duplicada/error, selector de módulo destino opcional, más selectores de **base y nivel destino** que se estampan en todas las filas del archivo). Badge de tipo: sky=V/F · violet=Múltiple · amber=Imágenes · slate=Texto libre. **Clasificación (Sprint 6)**: la barra de filtros suma dos `<select>` **encadenados** de Base y Nivel — no un `MultiSelectFilter` como los módulos, porque `?baseId=` es único y sobre todo porque **un nivel sólo existe dentro de una base**: con varias bases tildadas el filtro de nivel no significaría nada. Incluye la opción sintética **"— Sin clasificar —"** → `?sinBase=true`, que es cómo se encuentra el backlog previo a las bases. Elegir una base **fuerza la vista global** (mismo criterio que el buscador: la vista por-módulo lista pivots y no sabe filtrar por clasificación). La tabla global suma la columna **Base · Nivel** (badge indigo para la base, slate para el nivel; "Sin clasificar" en ámbar). El `NuevaPreguntaModal` suma los dos selects, con la Base **obligatoria** y el Nivel opcional y dependiente (se limpia al cambiar de base), y muestra la `fuente` que va a quedar congelada en la pregunta. |
| Bases | `bases-conocimiento` | **100% backend** (sin mock). ABM de la taxonomía del banco: cada base es un **tema** y adentro define su propia **escala ordinal** de dificultad. Va entre Preguntas y Reglas porque es donde se definen los temas con los que después se clasifica. **No usa `Table`**: es un acordeón por base (mismo motivo que Reglas — el layout anidado no encaja en columnas). Cabecera con nombre, badge de código, badge "Inactiva", contador de niveles y de preguntas, y la `fuente`; desplegada muestra el alcance (`descripcion`) y la escala editable. Sobre la escala: agregar (se appendea al final), **renombrar inline**, **subir/bajar con ▲▼** y eliminar. Reordenar **manda siempre la escala completa** (`PUT .../niveles/orden`), nunca un movimiento puntual — ver Sprint 6. Eliminar un nivel con preguntas se bloquea en el cliente con un aviso y en el backend con 409. Al crear una base se despliega sola, porque sin niveles todavía no sirve para clasificar. |
| Reglas | `assignment-rules` | **100% backend** (sin mock), ABM de `ReglaAsignacion` (`ReglasAsignacion.jsx`). Modal de alta con radio de alcance **"Todo el centro"**/**"Puestos específicos"** (en modo centro el multi-select de Puestos se oculta): en modo puestos arma el producto cartesiano puesto×módulo (como antes), en modo centro crea una regla de centro por cada módulo elegido. El listado **no es una tabla plana sino un acordeón por centro de costo**: como el alta arma el producto cartesiano puesto×módulo, una tabla plana repetía el centro en cada fila y no dejaba leer "qué tiene configurado este centro". Cada centro es una fila colapsable y **adentro las reglas se agrupan por alcance** (el puesto, o "todos los puestos"), con las de centro **primero**. Ese segundo nivel **no es un segundo acordeón**: los alcances están siempre visibles cuando el centro está abierto, son solo bloques separados por un divider. Se agrupó al sumar **"Editar módulos"**, que opera sobre el alcance y no sobre la fila: en la tabla plana anterior ese botón se repetía en cada fila del mismo puesto. Cada bloque tiene un sub-header (badge del puesto + cantidad de módulos + el botón "Editar módulos", una sola vez) y debajo una fila por módulo con su badge de estado y sus acciones. Con eso **`Table` dejó de usarse en esta pantalla** — el layout anidado no encaja en columnas, y una tabla por alcance repetiría el `<thead>` y perdería la alineación entre bloques. Se llevó puesto el prop `flush` que se le había agregado a `Table` para este caso: quedó sin ningún consumidor y **se eliminó del componente** (los 7 consumidores restantes nunca lo pasaban, así que ninguno cambia). El header del grupo llegó a tener el badge "Todos los puestos" y **se sacó**: colapsado no dice nada útil (el centro puede tener además reglas de par, así que no describe al grupo) y desplegado duplica el del sub-header. El header queda con nombre del centro + contador, nada más. **Se listan todos los centros activos, incluso los que no tienen ninguna regla** ("sin reglas") — sirve para detectar centros sin capacitación configurada; los centros dados de baja que conservan reglas aparecen al final con badge **"Centro inactivo"**, y esos grupos se derivan de las claves del índice de reglas, no filtrando el catálogo, para que una regla de un centro ausente del catálogo no desaparezca en silencio. **El filtro de alcance (Todas/Por puesto/De centro) se eliminó al pasar al acordeón**: existía porque en la tabla plana no se distinguía una regla de par de una de centro, y el badge del header más el orden dentro del grupo ya responden eso mejor — "De centro" además listaba los N centros con casi todos en "sin coincidencias". Sacarlo se llevó puesta la mayor parte de la complejidad del acordeón (el caso "sin coincidencias" distinto de "sin reglas", y que los contadores tuvieran que reflejar lo filtrado). Si en algún momento hace falta filtrar, el eje útil es **módulo** ("¿qué centros exigen Trabajo en Altura?") o un buscador por nombre de centro, no el alcance. Al guardar muestra el resumen "X nuevas · Y ya existían" — la comparación contra las reglas existentes normaliza `puestoId` `null`/`undefined` a un mismo sentinel para no contarlas como casos distintos. **Acciones**: **"Editar módulos"** una vez por alcance (en el sub-header), y por cada módulo **"Desactivar"/"Activar"** (la pausa reversible de siempre, que pasó de `danger` a `secondary` para no tener dos botones rojos juntos) y **"Eliminar"** (modal que explicita que la regla sale del listado, que **no se recupera desde el backoffice** y que las automáticas que justificaba se revocan en el acto, y que diferencia el caso de Desactivar).

**"Editar módulos" es por ALCANCE, no por fila, y reusa el modal del alta.** El alta siempre trabajó por alcance (centro + puestos × módulos), así que editar fila por fila era una asimetría: el mismo concepto se cargaba de una forma y se editaba de otra, y agregarle un módulo a un puesto ya configurado obligaba a volver a "+ Nueva regla" y reelegir centro y puesto. Es también el motivo por el que el listado agrupa por alcance (ver arriba): con la tabla plana el botón aparecía repetido en cada fila del mismo puesto. Ahora "Editar módulos" abre el **mismo** `Modal` con `mode: 'edit'`: el centro y el alcance quedan fijos (se muestran como contexto, no como controles deshabilitados — mover una regla de lugar sigue siendo eliminarla y crear otra) y el multi-select de Módulos arranca con los ya configurados de ese alcance tildados. **Se guarda por diff**: tildar → `POST` (crea o revive), destildar → `DELETE`. Dos detalles que importan:
- **El multi-select gobierna existencia, no el eje `activo`.** Una regla desactivada aparece tildada con el sufijo "· configurada (desactivada)" para que destildarla —que la **elimina**— no sea una sorpresa; dejarla tildada no la reactiva (para eso está el botón de fila). Los módulos dados de baja del catálogo que ese alcance ya tenga configurados también se agregan a las opciones, para no ofrecer destildarlos a ciegas.
- **El diff se previsualiza antes de aplicar** ("se agregan X · se eliminan Y") y, si hay eliminaciones, se listan por nombre con la misma advertencia del modal de Eliminar. Guardar está deshabilitado sin cambios; vaciar el set **sí** es válido (equivale a eliminar todas las reglas de ese alcance).

**Por qué el diff y no `PATCH { moduloId }`:** cambiar el módulo en el lugar conserva el `id` y el `createdAt` de la fila, así que la regla queda diciendo que **siempre** obligó al módulo nuevo — y sin AuditLog todavía, el módulo anterior no queda registrado en ningún lado. Alta + baja deja los dos hechos (la vieja con su `deletedAt`, la nueva con su `createdAt`). El endpoint `PATCH /reglas-asignacion/:id { moduloId }` existe y está testeado, pero **esta pantalla no lo usa**: queda disponible para cuando exista el AuditLog. Lo único que el frontend manda por `PATCH` es `{ activo }`. Después de cada mutación, **banner indigo** sobre el acordeón con el resumen del recálculo (`{usuarios, creadas, revocadas}`) — la consecuencia no se ve en el listado, lo que cambia son las asignaciones de otras personas. **El alta es secuencial, no `Promise.allSettled`**: cada POST abre ahora una transacción que recalcula todo el centro, y los N triples de una tanda comparten centro, así que mandarlos en paralelo eran N transacciones peleando por las mismas filas de `asignaciones`. Al acumular el resumen de la tanda, `usuarios` se combina con **máximo y no con suma** (es la misma gente en cada respuesta) — supuesto que hoy garantiza el modal con su `<select>` único de centro; si algún día se permite multi-centro por tanda, el máximo subcuenta y no hay arreglo del lado del cliente, porque la API devuelve un conteo y no los ids |
| Asignaciones | `training-assignments` | **100% backend** (sin mock), y **pantalla de CONSULTA por persona, no de acción** — el modelo real cambió el sentido de la pantalla: las asignaciones ya no se cargan una por una, las deriva el motor desde las `ReglaAsignacion` y los pares de cada persona; lo que aporta la pantalla es *"¿qué le corresponde a esta persona y por qué?"*. Es **por persona y no una tabla global** por un límite duro de la API: `GET /asignaciones` **exige** `?usuarioId=` y no existe endpoint que liste las de todo el mundo (construirla iterando sobre todos los usuarios serían N requests). Flujo: buscador por nombre o DNI contra `GET /usuarios` (tope 20 resultados) con estado vacío e instrucción mientras no haya nadie elegido → elegida la persona, **contexto** arriba (rol, organización, DNI) con los chips de sus **pares activos**, que son la causa de las automáticas; si no tiene ninguno se dice explícito ("sin pares activos — no le corresponde ninguna capacitación automática": es una cardinalidad válida y explica la ausencia). Después, tabla de **vigentes** (módulo · badge de origen **Automática** indigo / **Manual** slate · columna **"Por qué"**) con **"Revocar"** por fila (`PATCH /:id/revocar`, con confirmación), y las **revocadas** en una sección **colapsable** aparte con la fecha de revocación — no compiten visualmente con las vigentes pero están, porque el historial importa para ISO 9001. Botón **"Recalcular"** (`POST /asignaciones/recalcular/:usuarioId`, muestra `{creadas, revocadas}`): **dejó de ser parte del flujo normal** — los dos caminos que importan ya recalculan solos (tocar los pares de una persona y tocar una regla de su centro), así que el copy lo reformula como reconciliación manual "por si algo cambió por fuera de esos dos caminos". Ojo que **no** cubre dar de baja un Puesto/CentroCosto del catálogo: ahí no cambia nada, porque el motor no mira `Puesto.activo` (ver la sección del motor más abajo). **"+ Asignar manual"** se mantiene pero como excepción explícita: el modal avisa que una asignación MANUAL **no la toca el motor** (no se revoca sola si ningún par la pide) y traduce el 409 a un mensaje claro. Módulos sin versión publicada llevan el sufijo "(sin versión publicada)", mismo criterio que Reglas |

## App SIMA CHECK — flujo

Todas las pantallas son **tarjetas blancas** (`bg-white border border-slate-200 rounded-2xl shadow-2xl`) sobre un fondo claro con gradiente gris. Para usar imagen de fondo real, reemplazar el `background` inline en `App.jsx` por `backgroundImage: "url('/bg-industrial.jpg')"`.

El **logo** (`public/logo.png`) se renderiza en `App.jsx` encima de la card, visible en todas las pantallas.

1. **Ingreso por DNI** — campo numérico (`inputMode="numeric"`), botón INGRESAR, validaciones: vacío / DNI no encontrado
2. **Capacitaciones pendientes** — nombre y empresa del empleado + solo módulos con `assignment.status === 'pending'`; lista vertical de botones (`red-600`) con ícono y título; estado vacío si no hay pendientes
3. **Evaluación** — 3 preguntas aleatorias del módulo; barra de progreso avanza **al responder** (no al llegar); tipos de pregunta:
   - `truefalse`: 2 botones V/F (verde/rojo)
   - `multiple`: lista vertical, selección en `slate-900`
   - `image-options`: grid 2×2 de imágenes, selección con borde `red-600` + ring
   - Campo opcional `image` en cualquier pregunta: muestra la imagen del enunciado encima de las opciones (la ejercita la pregunta mock 112). Cuando la app se conecte al backend, `image` va a llegar como la URL armada desde `Pregunta.imagen` — `QuestionCard` no cambia, usa el `src` tal cual
4. **Resultado** — score %, badge APROBADO (≥70%) / DESAPROBADO (<70%), botones: Mis capacitaciones / Reintentar / Volver al inicio

Al finalizar una evaluación, la asignación cambia de `pending → completed` **solo si el empleado aprueba** (≥70%). Si desaprueba, queda `pending` y el módulo sigue apareciendo en la lista.

## Decisiones de arquitectura

- No se usa react-router intencionalmente.
- No existe persistencia entre sesiones — todo es estado local en React.
- **Regla de dependencia**: `sima-check/` puede importar de `core/`. `core/` nunca importa de `sima-check/`. `Dashboard` puede importar de ambos.
- El estado de `assignments` se eleva a `App.jsx` en la app tablet para permitir actualizaciones reactivas durante la sesión.
- Los modales manejan estado local.
- Los gráficos son SVG puro (sin librerías).
- Tailwind v3 es obligatorio.
- El campo `company` (string) se mantiene en el usuario de la app junto a `companyId` para evitar importar `companies.js` en la app tablet.
- **Los dos frontends nombran la entidad `usuario`, no `employee`** — alineado con el `Usuario` del backend, que unifica `User` + `Employee` (ver arriba). En la **app tablet** alcanza a los archivos (`data/usuarios.js`, `pages/UsuarioSelection.jsx`), al prop que se pasa entre pantallas (`usuario`) y al campo `assignments[].usuarioId`. En el **backoffice**, a `core/data/usuarios-mock.js` (export `usuariosMock`), al campo `trainingAssignments[].usuarioId` y a `evaluations[].usuarioName`. Los duplicados del modelo viejo (`sima-check-app/src/data/employees.js` + `pages/EmployeeSelection.jsx`, `sima-training-backoffice/src/core/data/employees.js`) se eliminaron; quedan en el historial de git. `User` (`core/data/users.js`) **no** entra en este rename: son las cuentas del backoffice (administrador/coordinador), otra cosa.
- La navegación de SIMA CHECK en el backoffice usa un Set (`SIMA_CHECK_PAGES`) en `BackofficeLayout.jsx` para detectar cuándo renderizar la barra de tabs y el breadcrumb de dos niveles.
- La pantalla Preguntas maneja su propia navegación interna (`selectedModuleId`) con `useState` — no requiere cambios en el router global.
- El campo `image` de las preguntas **mockeadas de la app tablet** es una ruta relativa a `public/` (ej: `/images/cartel.png`). En el backend, `Pregunta.imagen` ya no es eso: guarda una clave de storage y se sirve bajo `/uploads` (ver Sprint 4); las rutas a `public/` sobreviven solo como formato legacy del import de Excel.
- El tipo `image-options` usa las mismas rutas en `options[]` y `correctAnswer` — la comparación de respuesta correcta es por igualdad de string (misma ruta).

### Backend (Sprint 1)

- **Monolito modular por dominio**, no microservicios (un solo deploy). Cada entidad futura es un módulo NestJS nuevo, no un cambio transversal.
- **`Usuario` es una sola entidad** para toda persona. Unifica `User` + `Employee` del prototipo. El rol vivió transitoriamente en `Usuario` y ya se movió a `Vinculacion` (ver Sprint 5).
- **Trazabilidad** (`created_at/updated_at/created_by/updated_by`) y **soft-delete** (`deleted_at`) desde el día 1 — barato ahora, caro de retrofittear.
- **`datos` (jsonb)** en `Usuario` para nómina flexible. Hoy lo escribe únicamente el import de Excel, y desde que el import resuelve Puesto/Centro de Costo contra el catálogo real (ver "Import de usuarios" más abajo) es solo `legajo` (`src/import/import.service.ts`) — ya no hay mapeo abierto de columnas no reconocidas ni el viejo `puesto`/`sector` de texto libre. El ABM de Usuarios del backoffice ya no lo edita ni lo muestra (se sacó la sección "Datos de nómina" del modal — duplicaba `Puesto`/Centro de Costo con el catálogo real y el PATCH pisaba sin merge las columnas extra que dejaba el import).
- **Auth básica sin roles**: el backoffice se autentica con credenciales de entorno (`AUTH_USER`/`AUTH_PASSWORD`); el cliente front hace auto-login y cachea el token (no hay pantalla de login todavía). Lecturas abiertas, escrituras con JWT.
- **Deploy preparado, no activo**: `Dockerfile` + `render.yaml` listos; falta crear la cuenta cloud. CI (`.github/workflows/ci-sima-training.yml`) corre lint + build + test, sin deploy.
- **Local-first**: PostgreSQL corre en Docker Compose; requiere Docker Desktop.
- **Regla del clean del seed: toda entidad nueva que cuelgue de otra con FK `RESTRICT` tiene que sumarse a `limpiar()` (`prisma/seed.ts`), en orden de dependencia — de las hijas a las padres.** Casi todas las FK del schema son `ON DELETE RESTRICT` (las únicas dos que no: `Asignacion.moduloVersionId` y la self-FK `Organizacion.organizacionPadreId`, las dos `SET NULL`), así que una tabla nueva que no se agregue a esa cadena **bloquea el `deleteMany()` de su padre**. Ya pasó **tres veces**, siempre igual: `Asignacion` (FK **directa** a `Usuario`, no pasa por `Vinculacion`, así que es su propia rama), `ReglaAsignacion` (FK a `Modulo`/`Puesto`/`CentroCosto`) y `ModuloVersionCriterio` (tercera rama de `ModuloVersion`, además de bloquear el `baseConocimiento.deleteMany()` de `limpiarDemo()`, que corre después). Dos motivos por los que se escapa tan fácil:
  - **El síntoma aparece recién en la SEGUNDA corrida.** Sobre una base vacía no hay filas hijas que bloqueen nada, así que la corrida en la que se agrega la entidad pasa limpia y el error sale después, como un `..._fkey` opaco de la corrida siguiente. Por eso **la verificación de cualquier cambio al seed es correrlo dos veces seguidas**, no una.
  - **La cadena documentada en los comentarios de `limpiar()` puede estar incompleta** — es exactamente lo que falló las tres veces. Antes de reusarla o extenderla, grepear el `schema.prisma` entero por FKs hacia la tabla target en vez de asumir que está al día.

### Backend (Sprint 2 — SIMA CHECK)

- ~~**`clasificacion` persistida, no derivada**~~ — **revertido en el Sprint 5**: la columna `Usuario.clasificacion` se eliminó y la clasificación dejó de existir como concepto (se deriva de `Organizacion.tipo` + `organizacionPadreId`). Se registra acá porque la decisión original está citada en varios lugares del historial.
- **Banco de preguntas único**: `Pregunta` nunca se duplica; se comparte entre módulos vía el pivot `ModuloVersionPregunta`.
- **Módulos versionados e inmutables**: `Modulo` es un contenedor estable; editar su contenido crea una `ModuloVersion` nueva, la anterior queda `ARCHIVADO` y no se modifica.
- **Baja lógica de preguntas por módulo (no edición)**: regla de negocio deliberada — las preguntas no se editan, se activan/desactivan. Se agregó `activa` al pivot `ModuloVersionPregunta` (baja por módulo) en vez de reusar `Pregunta.activa` (global), para que desactivar afecte solo al módulo donde se hace. El toggle es in place sobre la versión vigente (no versiona): es la alternativa liviana explícita a editar contenido. La vista Preguntas del backoffice quedó 100% contra el backend (se eliminó el mock de esa pantalla; `training-modules.js` sigue para las demás, en migración).
- **Papelera global independiente de la baja por módulo**: `Pregunta.activa` (ya existía en el schema, sin usar) se activó como la baja lógica del banco entero. Enviar a papelera cascadea `activa=false` a los pivots de esa pregunta en versiones BORRADOR/ACTIVO — **nunca ARCHIVADO**, esas versiones son inmutables y no deben mutarse aunque sea para dar de baja una pregunta (bug corregido: el cascade original pegaba sobre todos los pivots sin filtrar por versión). Recuperar **no** restaura los pivots (asimetría intencional). Son dos ejes ortogonales: por-módulo (`ModuloVersionPregunta.activa`, el admin la maneja mientras arma un módulo puntual) vs. global (`Pregunta.activa`, "esta pregunta ya no sirve en ningún lado"). Para que estos dos ejes no queden inconsistentes, `ModulosService.setPreguntaActiva(id, true)` rechaza con `ConflictException` si la pregunta sigue en papelera global — si no, un admin podía "reactivar" el pivot de un módulo mientras el banco la seguía mostrando dada de baja. El backoffice refleja esto con un badge **"En papelera"** (distinto de "Inactiva") y sin botón de Activar en las vistas por-módulo, y con un modal de confirmación antes de enviar a papelera que lista los módulos afectados y avisa si alguno se queda sin preguntas activas (`totalActivasEnModulo`, calculado en `enriquecerConModulos`).
- **Filtro de módulo pasó de `<select>` único a multi-select con búsqueda** (`MultiSelectFilter.jsx`, componente nuevo reusable), con una opción sintética "Sin asignar" (no es un id real de `Modulo`, se traduce a `?sinAsignar=true`). El buscador de texto (`?q=`) es universal: cuando hay texto escrito, siempre se usa la vista global aunque haya 1 módulo seleccionado, para no tener que replicar la búsqueda en el camino por-módulo.
- **Detección de duplicados/similares resuelta en memoria**, no con `pg_trgm`/embeddings (decisión que revierte el TODO original): normalización de texto en español + coeficiente de Dice sobre trigramas de caracteres (`src/import/similitud.ts`), sin dependencias nuevas ni cambios de infraestructura de base. Motivo: el proyecto es local-first sin deploy cloud activo; atar la portabilidad a que el Postgres administrado permita `CREATE EXTENSION pg_trgm` no se justificaba a la escala actual del banco. Queda encapsulado en funciones puras, reemplazable el día que haga falta más escala.
- **Importación de preguntas con preview seleccionable fila por fila**: a diferencia de la importación de usuarios (todo-o-nada por fila, sin intervención), acá el preview clasifica cada fila (nueva/duplicada/parecida/error) y el usuario elige con checkboxes cuáles confirmar — necesario porque "parecida" es una señal de alerta, no un error automático a descartar. El confirm recibe esa selección como JSON (no vuelve a leer el Excel) con un `moduloId` de destino opcional.
- **Asignación pregunta↔módulo desde el backoffice (crear y editar), reusando endpoints existentes**: la relación ya vivía en el modelo (`ModuloVersionPregunta`); esta story la expuso en la UI sin agregar endpoints nuevos. Al **crear** una pregunta se elige el/los módulo(s) con un multi-select y se asigna a cada uno; al **editar** la asignación de una pregunta existente (vista global) el diff usa **asignar** para módulos nuevos, **reactivar** (`setPreguntaActiva true`) cuando el pivot ya existía inactivo —evita el `P2002` del PK compuesto— y **baja lógica por módulo** (`setPreguntaActiva false`) para quitar. "Quitar" no borra el pivot (queda tachado en la columna Módulos); un unassign duro (DELETE del pivot) queda como refinamiento futuro. Para soportar el alta multi-módulo sin calcular `orden` por módulo en el cliente, `asignarPreguntas` ahora **appendea** el `orden` cuando el item no lo trae. `asignarPreguntas` apunta a la versión BORRADOR y `setPreguntaActiva` a la vigente (ACTIVO-o-última); desde Sprint 3 (versionado real) ambas pueden divergir — ver limitación conocida más abajo.

### Backend (Sprint 3 — Versionado de módulos)

- **Numeración pública de 3 partes `AÑO.MAYOR.MENOR`** (ej. `2026.01.00`), distinta del `numeroVersion` interno (contador monotónico de creación, usado solo para ordenar/versionar internamente). El número público se asigna **recién al Activar** (publicar); un borrador sin publicar no tiene número y se muestra como "Borrador". Semántica: **Actualización** (misma línea) sube MENOR (`2026.01.00 → 2026.01.01`); **Versión nueva** sube MAYOR y resetea MENOR (`→ 2026.02.00`); MAYOR es la secuencia del módulo **por año** (primera publicación del año = `01`).
- **La elección actualización/versión nueva (`esNuevaLinea`) se decide recién al Activar, no al crear el borrador** — decisión revertida respecto al diseño original de este sprint. Al principio se preguntaba al crear el borrador (`POST /:id/versiones`) y se guardaba de entrada; se cambió porque no tiene sentido comprometerse a esa elección antes de saber cuánto se va a terminar modificando. `crearVersion` ya no recibe `esNuevaLinea` ni lo persiste; `activar(moduloId, esNuevaLinea?)` lo recibe como parámetro y recién ahí lo escribe en el `ModuloVersion` (`esNuevaLinea: activo ? esNuevaLinea : null`). Es obligatorio (el service tira `ConflictException` si falta) únicamente cuando ya hay un ACTIVO publicado del cual derivar el número; en la primera publicación no hay de qué elegir y queda `null`. El endpoint `PATCH /:id/borrador` (`actualizarEleccionBorrador`) que existía para cambiar la elección a mitad de edición se eliminó por completo — ya no hace falta, ahora todo pasa por el modal de Activar.
- **A lo sumo un BORRADOR y un ACTIVO por módulo.** `crearVersion` rechaza si ya hay un borrador en curso (hay que activarlo o cancelarlo primero, ver `cancelarBorrador` más abajo) o si no hay un ACTIVO del cual partir (primera publicación no pasa por esta elección: se edita directo el v1 y se activa). Crea el borrador **copiando los pivots** (`ModuloVersionPregunta`) del ACTIVO, así el punto de partida de la edición es el contenido publicado, no uno vacío.
- **`activar` es transaccional**: en la misma transacción, calcula el número (según el `esNuevaLinea` recibido en el body y el ACTIVO base), pasa el borrador a `ACTIVO` con ese número + `activadaEn` + `esNuevaLinea`, y el ACTIVO anterior (si había) a `ARCHIVADO` — nunca quedan dos `ACTIVO` simultáneos.
- **`cancelarBorrador` (descartar el borrador en curso)**: borra el `ModuloVersion` en BORRADOR, sus pivots `ModuloVersionPregunta` y sus `ModuloVersionCriterio` (las FK son `ON DELETE RESTRICT`, así que hay que borrar los hijos antes que la versión, en una transacción). Si el módulo tenía un ACTIVO, queda tal cual estaba antes de empezar a editar. Si el borrador era su única versión (el módulo nunca se publicó), no tiene sentido un módulo sin ninguna versión, así que la misma operación borra el `Modulo` entero — el backoffice etiqueta el botón distinto según el caso ("Cancelar borrador" vs "Eliminar módulo") pero es el mismo endpoint y el mismo método de servicio. El modal de confirmación de **"← Volver"** (dentro del editor del borrador) reusa este mismo flujo para su opción "Descartar": no duplica lógica, solo abre el modal de cancelar-borrador ya existente en vez de tener su propio handler.
- **`unassignPregunta` (unassign duro) vs `setPreguntaActiva` (baja lógica) — cuándo usar cada uno.** Ambos actúan sobre `versionParaEditar` (BORRADOR en curso si existe, si no la vigente), pero `unassignPregunta` además exige `version.estado === 'BORRADOR'` y tira `ConflictException` si no — a diferencia de `setPreguntaActiva`, que sí puede togglear sobre una versión ya publicada (es reversible, no rompe inmutabilidad). Borrar un pivot de una versión ARCHIVADO/ACTIVO sí rompería la inmutabilidad del historial, por eso el hard-delete está limitado al borrador. En el backoffice, el editor del borrador ofrece ambos como acciones independientes por fila ("Desactivar", gris/secondary — "Quitar", rojo/danger), no una reemplaza a la otra: "Desactivar" es reversible sin perder la fila, "Quitar" saca la pregunta del todo (hay que reasignarla desde el banco si te arrepentís).
- **`findVersiones` devuelve `preguntasCount`** (no la lista completa de preguntas) para el historial; el detalle de una versión puntual con sus preguntas es un endpoint aparte (`GET /:id/versiones/:versionId`), reservado para cuando el backoffice necesita mostrar el contenido real (evita traer preguntas de más al listar el historial).
- **El backoffice reusa la vista de solo-lectura para dos casos** (ver preguntas del ACTIVO vigente, y ver el detalle de una versión archivada del historial) en vez de duplicar UI: ambos son "mostrar las preguntas de una versión puntual, sin poder editarlas", solo cambia de qué versión.
- **`versionParaEditar` vs `ultimaOActivaVersion` — resuelto el gotcha de edición sobre la versión equivocada.** `findOne` y `setPreguntaActiva` usan `versionParaEditar` (BORRADOR en curso si existe, si no la vigente publicada) en vez de `ultimaOActivaVersion` (ACTIVO-o-última, ignora si hay un borrador). Antes de este ajuste, con un ACTIVO y un BORRADOR coexistiendo, togglear una pregunta desde `Questions.jsx` (pantalla Preguntas, vista por-módulo) afectaba por error a la versión **publicada** en vez de al borrador en edición. `versionesVigentesDe` (reportes/enriquecimiento de `PreguntasService`, "qué módulos publicados tiene esta pregunta") sigue usando `ultimaOActivaVersion` sin cambios — ahí sí interesa lo publicado, no el trabajo en progreso.
- **Sacar preguntas del borrador — dos formas, a propósito.** `PreguntasAsignadasPanel` (compartido entre Preguntas y Módulos) acepta `onToggle` y `onRemove` opcionales, independientes entre sí. `onToggle` es la baja lógica de siempre (`setPreguntaActiva`): la fila queda atenuada con badge "Inactiva", se puede reactivar, y funciona tanto en un borrador como en la vigente publicada. `onRemove` es el unassign duro (`unassignPregunta`): borra el pivot del todo, la fila desaparece — solo tiene sentido en un BORRADOR (el backend lo rechaza sobre ACTIVO/ARCHIVADO, inmutables). En el editor de borrador de Módulos ambos son **locales** (staged, ver bullet siguiente) — no pegan al backend hasta Guardar/Activar; las vistas read-only (ver vigente, detalle del historial) no pasan ninguno de los dos y quedan de solo lectura.
- **Staging real en el editor de borrador de Módulos — nada se manda al backend hasta "Guardar y volver" o "Activar".** Diseño revertido respecto a las primeras versiones de esta pantalla (donde cada acción —asignar, activar/desactivar, quitar— pegaba al backend al toque). `TrainingModules.jsx` mantiene `localAsignadas`, una copia editable que arranca como foto de `banco.asignadas` una sola vez por sesión de edición (una `sessionKeyRef` con `${moduleId}:${versionId}` evita retomar la foto en cada render, solo cuando se entra a otro borrador); mientras se edita, `banco.asignadas` no se vuelve a pedir. Los handlers de fila (`handleTogglePreguntaLocal`, `handleQuitarPreguntaLocal`, `handleAsignarLocal`, `handleNuevaPreguntaLocal`) solo mutan ese estado local, sin `await` ni loading — no hay red de por medio. `flushCambios()` diffea `banco.asignadas` (foto del server al entrar) contra `localAsignadas` (lo armado) y dispara la mínima cantidad de llamadas (`unassignPregunta` para lo sacado, `asignarPreguntas` para lo nuevo, `setPreguntaActiva` para lo que cambió de activo/inactivo); la usan tanto "Guardar y volver" como "Activar" (que primero flushea y recién después publica, para que lo publicado incluya los cambios de la sesión). `AsignarPreguntaModal`/`NuevaPreguntaModal`/`BancoAcciones` ganaron un `onAssign`/`onAssignExisting`/`onAssignNew` opcional: si el padre lo pasa, el modal le devuelve lo elegido en vez de pegarle al backend él mismo — la vista por-módulo de Preguntas (`Questions.jsx`) no lo pasa y sigue guardando de inmediato como siempre, ese camino no es staged.
- **"Descartar" en el modal de Volver ahora es liviano — no delega a `cancelarBorrador` salvo un caso.** Como nada se mandó al servidor durante la sesión, descartar cuando el módulo **ya tiene un ACTIVO** publicado es solo no flushear y navegar (el borrador queda con lo que tenía guardado de sesiones anteriores, si las hubo). La excepción es el módulo **nunca publicado**: ahí no hay ACTIVO al cual volver, así que "Descartar" sigue delegando al flujo completo de `cancelarBorradorModal` (elimina el módulo entero) — mismo criterio que el botón standalone "Cancelar borrador"/"Eliminar módulo", que sigue existiendo sin cambios y sigue siendo la única vía para tirar sesiones ya guardadas anteriormente, no solo la actual.
- **Recomendar "versión nueva" cuando el borrador acumula muchos cambios — mostrado dentro del modal de Activar, no durante la edición.** Se compara el borrador contra el ACTIVO del que partió (preguntas activas agregadas + quitadas, `contarCambios`/`deberiaRecomendarVersionNueva` en `TrainingModules.jsx`). Si los cambios llegan a `RECOMENDAR_MIN_CAMBIOS` (2) **y** son ≥30 % de las preguntas de la base, al abrir el modal de "Activar" (con la opción "Actualización" seleccionada, que es el default) aparece una advertencia ahí mismo sugiriendo elegir "Versión nueva" en su lugar — el usuario puede simplemente clickear esa opción antes de confirmar, no hace falta un endpoint aparte para "cambiar de opinión" a mitad de edición. Motivo: sin este aviso, alguien podría encadenar puras "actualizaciones" hasta que el módulo termine siendo completamente distinto sin que la línea mayor lo refleje nunca. El umbral es una heurística simple (constantes en el componente), ajustable si en la práctica resulta muy sensible o muy laxo.
- **Compartir un borrador como versión beta (diseño, sin implementar):** para que un tester pruebe un borrador sin activarlo ni afectar las estadísticas de la versión publicada. Propuesta: un `betaToken` (+ opcional `betaExpiraEn`) sobre el `ModuloVersion` en BORRADOR, generado al "Compartir"; `POST /modulos/:id/beta` para generar/rotar el token y un endpoint público `GET /modulos/beta/:token` que sirva las preguntas del borrador. Bloqueado hasta que la app tablet se conecte al backend (hoy sigue 100% mockeada, no hay dónde correr el modo beta); cuando se implemente, decidir si las respuestas del modo beta se persisten (feedback) o son efímeras — probablemente efímero al principio, y sumar persistencia cuando exista el modelo de respuestas/estadísticas por pregunta.

### Backend (Sprint 4 — Imágenes en el enunciado)

- **`Pregunta.imagen` ya existía en el schema pero estaba muerto**: el POST y el import de Excel lo aceptaban, pero no había forma de subir el binario ni de servirlo, y el backoffice nunca lo seteaba (solo pintaba un 🖼 si venía del Excel). Este sprint cerró las dos brechas, sin migración de datos ni cambio de schema.
- **Storage detrás de una interfaz chica, para que migrar a S3 sea barato.** `StorageService` (abstracto) expone solo `guardar(buffer, carpeta, extension) → clave` y `borrar(clave)`; `LocalDiskStorage` escribe en `UPLOADS_DIR` (default `./uploads`, gitignoreado) y `main.ts` lo sirve con `useStaticAssets` bajo `/uploads` (se eligió sobre `ServeStaticModule` para no sumar `@nestjs/serve-static`: son dos líneas y `platform-express` ya estaba). **La base guarda una clave opaca, nunca una ruta de filesystem ni una URL absoluta** — eso es lo que hace que migrar a S3 sea escribir otra implementación de la clase, sin tocar schema, controllers ni frontend. Al deployar hay que montar un disco persistente en `UPLOADS_DIR`, o migrar a S3 ahí mismo.
- **El formato se detecta por magic bytes, no por `originalname` ni `mimetype`** (`storage/formato-imagen.ts`, funciones puras al estilo de `import/similitud.ts`): los dos son input del cliente y se pueden mentir. La extensión con la que se guarda sale del tipo detectado, y el nombre es siempre un uuid generado — construir un path con el `originalname` sería path traversal. Límite de 2 MB (multer aborta con 413; el service revalida para dejar el mensaje en castellano si esa red falla).
- **La subida va separada del alta (dos pasos), no como un multipart único.** `POST /preguntas/imagen` devuelve la clave y `POST /preguntas` sigue siendo el mismo JSON de siempre con esa clave en `imagen` — así el `CreatePreguntaDto` no cambió, y el modal puede mostrar el preview antes de confirmar. En el frontend el archivo **se queda en el browser hasta confirmar**: por eso quitar/cambiar la imagen antes de crear es estado local, y abrir y cerrar el modal no genera huérfanos. La única fuente de huérfanos es que el alta falle después de subir, y para eso está `DELETE /preguntas/imagen/:clave`, que el modal llama en su catch (ignorando el error de limpieza para no tapar el del alta).
- **La imagen de una pregunta ya creada no se reemplaza ni se borra — decisión de diseño, no una limitación pendiente.** Respeta la regla vigente ("las preguntas no se editan, se activan/desactivan": no hay endpoint de edición) y, sobre todo, la inmutabilidad del historial: todas las versiones de módulo comparten el mismo `preguntaId` (`crearVersion` copia el pivot, no la pregunta), así que mutar `imagen` cambiaría retroactivamente versiones `ARCHIVADO` que deben seguir mostrando lo que se rindió. Para cambiarla: papelera + pregunta nueva, igual que para corregir un texto. El backend lo hace cumplir: `DELETE /preguntas/imagen/:clave` responde **409** si alguna pregunta referencia la clave, y valida la forma exacta de la clave (regex) para no ser un borrado arbitrario de archivos. La papelera **no** borra el archivo: `setActiva(false)` es reversible.
- **Que la imagen "se copie" al generar un borrador salió gratis**, sin código: `imagen` vive en `Pregunta` y las versiones comparten el `preguntaId`, así que el borrador ve la misma imagen. Verificado end-to-end; el mecanismo ya estaba cubierto por el test de `crearVersion` que fija la copia de pivots.
- **`imagenUrl()` (backoffice, `core/api/preguntas.js`) centraliza la traducción clave → URL** porque conviven dos formatos: la clave opaca nueva (se prefija con `${BASE_URL}/uploads/`) y las rutas relativas a `public/` que escribe el import de Excel (`/images/cartel.png`), que se usan tal cual. Por eso `BASE_URL` pasó a exportarse desde `client.js`.
- **Las opciones de `OPCIONES_IMAGEN` también se suben** (antes eran rutas tipeadas a mano en el form: había que dejar el archivo en `public/` por fuera del sistema y escribir la ruta exacta). Reusan el mismo endpoint y la misma carpeta `preguntas/` que el enunciado — son todas imágenes de preguntas, no hacía falta separarlas. Las rutas legacy del import de Excel se siguen renderizando vía `imagenUrl()`.
- **La opción correcta se trackea guardando el `File`, no un índice ni un texto.** Cuando se elige cuál es la correcta, las claves **todavía no existen**: se generan al subir, y la subida pasa recién al confirmar (patrón de la Story 5 que evita huérfanos). Guardar la referencia al `File` evita además que la marca se desincronice al quitar o reemplazar un slot. En `handleGuardar` se traduce a clave tomando la que quedó en su misma posición del **array compactado** (`opciones[files.indexOf(correctaFile)]`): los slots vacíos no viajan, así que un hueco en el medio (ej. `[A, vacío, C, D]`) no debe desalinear la respuesta correcta — está verificado con imágenes de contenido distinguible.
- **El `<select>` de respuesta correcta no aplica a `OPCIONES_IMAGEN`** (no hay texto que mostrar, y con claves opacas el label sería `preguntas/<uuid>.png`): se elige tocando la miniatura, como en la app del alumno. Para `VERDADERO_FALSO`/`OPCION_MULTIPLE` el select queda igual.
- **`borrarImagen` mira los dos lugares donde puede vivir una clave**: la columna `imagen` (enunciado) y el jsonb `opciones` (`OR` con `array_contains`). Mirar solo la columna —como hacía al principio— dejaba borrar una imagen de opción en uso, rompiendo la pregunta en silencio.
- **Validación de opciones en `PreguntasService.create`** (`validarOpciones`): los tipos con opciones requieren ≥2, y `respuestaCorrecta` (opcional) debe ser una de ellas. Va en el service y no en el DTO porque son reglas cruzadas entre campos, que class-validator no expresa. Se agregó junto con las opciones-como-archivo porque con textos legibles un desalineamiento se veía a simple vista y con claves opacas es invisible: rompería la corrección de la evaluación sin que nadie lo note. El import de Excel entra por el mismo `create()`, así que su **preview** adelanta la misma comprobación de membresía (junto al `opciones.length < 2` que ya tenía) para que la fila se marque como `error` y se pueda destildar, en vez de que el confirm falle a mitad de la importación.

Con rutas mock funciona; el día que la app se conecte al backend hay que traducir clave → URL ahí también (equivalente de `imagenUrl`), manteniendo la clave cruda como identidad para que `calculateScore` siga comparando bien.

### Backend (Sprint 5 — Modelo de vinculación)

Diseño completo y razonado en [`docs/modelo-vinculacion.md`](docs/modelo-vinculacion.md). Lo que quedó implementado:

- **`Usuario` es identidad pura; la pertenencia vive en `Vinculacion`.** `rol`, `organizacionId` y `clasificacion` se fueron de `Usuario`. `Vinculacion` tiene `usuarioId @unique` — la regla "una sola organización por persona" **es el índice**, no disciplina del service. El ABM sigue siendo uno solo (`/usuarios`): la vinculación se crea y edita **anidada** en el mismo request, no tiene endpoints propios.
- **Puesto y centro de costo van apareados en `VinculacionPuestoCentro`, no como ejes independientes.** La capacitación obligatoria depende del par (*"Soldador en YPF" ≠ "Soldador en PAE"*); con dos listas sueltas alguien con puestos {Soldador, Amolador} y centros {YPF, PAE} se leía como habilitado para cualquier combinación. Por eso el filtro `?puestoId=&centroCostoId=` del listado es **exacto**: devuelve a quien ejerce ese puesto *dentro de* ese centro, no a quien tiene los dos por separado.
- **`principal` es solo display, y se maneja al mínimo a propósito.** El alumno rinde los módulos de **todos** sus pares, así que el principal no decide nada: solo qué fila puesto/centro muestra el listado. El primer par de una vinculación queda principal y listo — sin herencia automática al desactivar, sin promoción de otro par, sin specs (no vale la pena testear algo cosmético). La única cautela técnica es que un eventual swap de principal necesita **dos UPDATEs en una transacción**, porque el índice único parcial (`WHERE principal AND activo`) no es diferible; hoy no hay ningún flujo de swap y no se construyó uno.
- **La matriz tipo-de-organización ↔ rol se valida en el service y la comparten alta manual e import.** Vive en `src/usuarios/matriz-rol-organizacion.ts` como una función pura que devuelve el motivo del rechazo o `null` — no lanza, para que el alta la convierta en 400 y el import la reporte como error de esa fila sin abortar el archivo. **El import no reimplementa nada**: `ImportService.confirmarUsuarios` arma un `CreateUsuarioDto` por fila y llama a `UsuariosService.create(dto, 'import')`, así que hereda validación, revive-por-DNI y trazabilidad. Efecto colateral esperado: una nómina de ALUMNOs apuntada a una organización `CLIENTE` ahora se rechaza fila por fila (CLIENTE solo admite AUDITOR); por eso el Excel acepta una columna `rol` opcional. Y como `Vinculacion.organizacionId` es NOT NULL, una fila cuya empresa no resuelve pasó de "usuario huérfano sin organización" a **error de fila**.
- **El listado no oculta a nadie por no tener pares.** Los filtros de vinculación se agregan al `where` **solo si vienen**: sin filtros, aparecen también las personas con cero pares (el pivote arranca vacío, es una cardinalidad válida) y su `parPrincipal` viaja en `null`. Filtrar por puesto/centro es lo único que las deja afuera, y ese filtro mira solo pares con `activo: true` — un par dado de baja no cuenta como "trabaja ahí".
- **Lista y detalle devuelven la misma forma** (un solo `include` compartido, `USUARIO_INCLUDE`): `vinculacion: { rol, organizacion, parPrincipal, pares }`. Se devuelve `pares` completo además del principal para no tener dos contratos distintos según el endpoint.
- **Reemplazo completo de pares en el PATCH, no merge**: mandar `pares` borra los que había y crea los de la lista, dentro de una transacción y borrando **antes** de crear (por el índice único parcial de `principal`). Omitir `pares` deja los existentes intactos.
- **El seed borra en orden de dependencia**: `Asignacion` → `VinculacionPuestoCentro` → `Vinculacion` → `Usuario`/`Organizacion`. Todas las FK son `ON DELETE RESTRICT`; el orden original (`usuario.deleteMany()` primero) sobrevivía solo porque la base no tenía vinculaciones — con una sola vinculación sembrada revienta con `vinculaciones_usuario_id_fkey`. **`Asignacion` fue el segundo bug del mismo tipo**: se agregó al modelo después de escribirse este comentario y tiene una FK **directa** a `Usuario` (no pasa por `Vinculacion`), así que quedó fuera del orden documentado hasta que una limpieza de usuarios con asignaciones cargadas lo hizo fallar con `asignaciones_usuario_id_fkey`. Antes de reusar/extender este orden si se agrega una tabla nueva con FK a `Usuario`, grepear el schema entero por el nombre de la tabla en vez de asumir que la cadena documentada sigue completa.
- **Los frontends ya consumen la forma nueva.** `Usuarios.jsx` lee y escribe `vinculacion` anidada (`vinculacion.rol`, `vinculacion.organizacion`, `vinculacion.pares`, `parPrincipal`) y suma el ABM de pares; `clasificacion` no aparece en ningún frontend. La app tablet nunca tuvo `rol`/`clasificacion` en su mock, así que no requería migración. Lo que queda mockeado son otras entidades (clientes, evaluaciones), no la forma de `Usuario`.

### Backend (Asignaciones automáticas por par)

- **`ReglaAsignacion` es el motor de las `Asignacion` automáticas.** El par exacto (puesto, centro de costo) —no cada eje por separado, mismo criterio que `VinculacionPuestoCentro`— obliga a rendir un módulo. Apunta a `Modulo` (el contenedor), no a una `ModuloVersion`: la obligación es "este módulo", la versión concreta que se rinda se resuelve al momento de rendir. El `@@unique([puestoId, centroCostoId, moduloId])` hace que volver a cargar una regla dada de baja la reactive en vez de duplicarla.
- **`Asignacion` nunca se borra, se revoca** (`revocadaAt`). Un índice único parcial (`WHERE revocada_at IS NULL`, vive solo en la migración SQL — Prisma no expresa `WHERE` en `@@unique`, mismo caso que el `principal` de `VinculacionPuestoCentro`) garantiza a lo sumo una asignación vigente por (usuario, módulo).
- **`recalcular(usuarioId)` es síncrono, idempotente, y nunca toca las `MANUAL`.** Pasos: (1) trae los pares ACTIVOS de la vinculación; (2) arma la unión de módulos requeridos por las reglas vigentes que matchean algún par (un módulo pedido por dos pares genera una sola asignación, es un `Set`); (3) resta los módulos ya aprobados (hueco, ver abajo) y los ya cubiertos por cualquier vigente; (4) crea las `AUTOMATICA` que faltan; (5) revoca las `AUTOMATICA` vigentes cuyo módulo ya no está en `requeridos` — usando `requeridos` sin restar aprobados, para no revocar un módulo aprobado que un par sigue pidiendo, solo evitar recrearlo. Correr `recalcular` dos veces seguidas no duplica ni revoca de más.
- **Ya no es solo un endpoint aparte** (`POST /asignaciones/recalcular/:usuarioId` se mantiene para recalcular a demanda). Se agregó el auto-invoke desde `UsuariosService` en un cambio posterior. Los guards son asimétricos a propósito:
  - `create()` **rama normal**: recalcula **solo si el alta trae pares**. Sin pares no hay nada que derivar (requeridos = ∅, vigentes = ∅), así que es un `create` plano sin transacción — es el camino del import de nómina.
  - `create()` **rama revive** (alta sobre un DNI dado de baja): recalcula **siempre, sin guard**. Un usuario revivido puede arrastrar `AUTOMATICA` vigentes de antes de la baja, así que aunque reviva sin pares hay que revocar las que ya no correspondan.
  - `update()`: recalcula **solo si el request tocó `pares`** (`puestosCentros !== undefined`). Cambiar nombre/rol/organización no lo dispara; mandar `pares: []` (vaciar) **sí**, para revocar las que sobran.
  - `remove()`: **no recalcula nada** — solo setea `deletedAt`, y deja las asignaciones vigentes tal cual. Es exactamente el motivo por el que la rama de revivir no lleva guard.
- **Eliminar una regla es baja lógica, no un `DELETE` — y convive con `activo` a propósito.** La duda razonable es por qué hay dos ejes de baja habiendo ya `activo`. `activo` es la **pausa reversible** (la regla sigue en el listado del backoffice y se reactiva con un click); eliminar es sacarla de la vista para siempre, que es lo que hace falta cuando una regla se cargó por error o el par dejó de existir — dejarla desactivada para siempre ensucia el acordeón. Ahora bien, **la fila nunca se borra**: `remove()` setea `deletedAt` y nada más. Es la única evidencia de por qué una persona tuvo que rendir un módulo, y de cara al AuditLog ISO 9001 no puede desaparecer — sobre todo mientras el vínculo asignación→regla no se persista (hoy el "por qué" se recalcula en el cliente, ver `docs/pendientes.md`). O sea que la convención del dominio (nada se borra físicamente: `Asignacion` revoca, `Pregunta` va a papelera, los catálogos usan `activo`) **se respeta**; lo irrecuperable es sólo el acceso desde el backoffice, que no lista las eliminadas ni tiene filtro para verlas. Recrear el mismo triple **revive esa misma fila** (mismo `id`, misma trazabilidad), así que "eliminé sin querer" se resuelve volviéndola a cargar.
- **Cambiar una REGLA también recalcula** (cerró la asimetría que había con el ABM de usuarios). `ReglasAsignacionService` inyecta `AsignacionesService` y las tres mutaciones (`create`/`update`/`remove`) llaman a `recalcularCentro()` **dentro de la misma transacción** que cambió la regla: si algo falla se revierte todo junto y no quedan asignaciones derivadas de una regla que no se guardó. El fan-out es acotado y no hace falta un job en background — a quien alcanza una regla, de cualquiera de los dos alcances, es siempre alguien con un par **activo** en ese centro de costo, así que el centro alcanza como filtro (`usuariosAlcanzados`, que además excluye usuarios dados de baja: `recalcularEnTx` los rechaza con un 404 que abortaría la transacción entera). El timeout de la transacción se sube a 15 s (el default de Prisma son 5) porque adentro corre un recálculo por persona.
- ⚠️ **Lo que sigue SIN recalcular: dar de baja un `Puesto` o un `CentroCosto` del catálogo.** `recalcularEnTx` mira `VinculacionPuestoCentro.activo` y `ReglaAsignacion.activo`/`deletedAt`, **nunca** `Puesto.activo` ni `CentroCosto.activo`, y ni `PuestosService` ni `CentrosCostoService` inyectan el motor. Los pares y las reglas que apuntan a un puesto dado de baja siguen vivos y siguen generando obligaciones — y **`POST /asignaciones/recalcular/:usuarioId` tampoco lo corrige**, porque el motor ignora ese flag. Verificado contra la API. Puede ser el comportamiento correcto (el `activo` de los catálogos significa "no ofrecerlo más en los selects", no "invalidar lo ya cargado"), pero está sin decidir explícitamente — ver `docs/pendientes.md`.
- **El registro de aprobaciones es un hueco explícito**, aislado en `AsignacionesService.modulosAprobados()` (devuelve un `Set` vacío hasta que exista la entidad — bloqueado por la conexión de la app tablet y su flujo de rendir evaluación). Cuando exista, se completa solo ahí: `recalcular` ya la consume en el paso de creación, así que "si ya aprobó, no vuelve a tener que rendir aunque le corresponda por un par nuevo" queda cubierto sin tocar el resto de la lógica. `Asignacion.moduloVersionId` queda `null` por el mismo motivo — se completa recién al rendir.
- **El backoffice ya tiene las dos pantallas** (`ReglasAsignacion.jsx` y `TrainingAssignments.jsx`, ver la tabla de SIMA CHECK). La de Asignaciones reemplazó al mock viejo de HSE y cambió de sentido: **es de consulta, no de acción**, porque las asignaciones las deriva el motor y no se cargan a mano.
- **La explicabilidad de una asignación se deriva en el cliente — lógica duplicada a propósito.** Ningún endpoint devuelve *por qué* existe una `Asignacion`, así que la columna "Por qué" de la pantalla reimplementa en el frontend el mismo matching que `recalcularEnTx`: trae `GET /reglas-asignacion?activo=true` y para cada `AUTOMATICA` busca una regla del mismo módulo que matchee (a) el par exacto puesto+centro, o (b) `puestoId === null` con el centro de algún par activo. Se aceptó la duplicación en vez de agregar un campo `motivo` a `Asignacion` (que habría que mantener consistente en cada recálculo) o un endpoint de explicación; el costo es que si el matching del backend cambia, hay que tocar los dos lados. Cuando no encuentra ninguna regla que la justifique muestra **"Regla desconocida"** en ámbar en vez de inventar una explicación. Ese caso **se volvió raro** desde que tocar una regla recalcula en el acto (antes era el síntoma esperado de una regla desactivada sin recalcular): lo que queda son residuos —asignaciones derivadas antes de que el recálculo fuera automático, o datos cambiados por fuera de la app— y el hecho de que la pantalla trae las reglas **una sola vez al montar**, así que si otra sesión edita una regla mientras tanto, acá se ven viejas. Sigue siendo la señal que justifica apretar "Recalcular".

### Backend (Import de usuarios — resolución de Puesto/Centro de Costo)

- **El import de nómina dejó de guardar Puesto/Centro de Costo como texto libre y pasó a resolverlos contra el catálogo real** (`Puesto`/`CentroCosto`), creando el par `VinculacionPuestoCentro` de cada usuario importado igual que si se hubiera cargado a mano. Antes de este cambio esas dos columnas iban al jsonb `datos` sin validar, así que un usuario importado no aparecía con Puesto/Centro en ningún listado del backoffice hasta que un admin se lo cargaba después a mano — el objetivo era cerrar ese hueco, no solo mostrar el texto.
- **Reusa el matching de `similitud.ts` en vez de reinventarlo** (mismo mecanismo que el import de preguntas: normalización en español + coeficiente de Dice sobre trigramas, `UMBRAL_PARECIDA = 0.7`). El campo `preguntaId` de `RefSimilitud`/`ClasificacionCatalogo` es el nombre genérico que ya define ese archivo compartido — no vale la pena tocarlo solo por naming al reusarlo para `puestoId`/`centroCostoId`.
- **`previewUsuarios` clasifica pero NO empuja las filas nuevas de vuelta a `refs`** — a diferencia de `previewPreguntas`, que sí lo hace para detectar duplicados intra-archivo. Acá, dos filas con el mismo puesto nuevo ("Pintor" x2) deben salir **ambas** `'nueva'` de forma independiente: el catálogo real todavía no tiene "Pintor", así que la 2ª fila no es "duplicada de la 1ª". El dedupe de "crear este catálogo nuevo una sola vez" queda del lado del frontend, agrupando por texto normalizado.
- **`confirmarUsuarios` pasa a ser JSON puro, no multipart** (mismo patrón que `confirmarPreguntas`): el Excel no se re-sube, el frontend manda las filas ya resueltas con `puestoId`/`centroCostoId` reales. Son obligatorios a nivel de DTO (`@IsUUID()` sin `@IsOptional`) — la regla de negocio "nunca un usuario activo sin puesto y centro de costo" queda garantizada estructuralmente, no por convención de service.
- **Crear catálogo nuevo lo dispara el frontend** (`ImportUsuariosModal.jsx`, `crearOResolverCatalogo`), llamando a los endpoints ya existentes `POST /puestos`/`POST /centros-costo` — el import no abre una transacción propia para esto. Si dos filas piden crear el mismo puesto nuevo, el frontend agrupa por texto (`claveGrupo`, trim + lowercase) y crea **una sola vez**; si aun así el `POST` choca con el `@unique` de nombre (otra fila o otro admin lo creó en el medio), `crearOResolverCatalogo` recupera el id buscándolo en el catálogo recién refrescado en vez de abortar.
- **UI de revisión (`ImportUsuariosModal.jsx`), 3 pasos**: *seleccionar* (archivo + organización, igual que antes) → *revisión*: tabla con checkbox por fila (`EstadoSimilitudBadge` compartido con el import de preguntas, `estadoSimilitudBadge.jsx`) y, debajo, un **resolver por grupo** (`GrupoResolver`) separado para Puestos y para Centros de Costo — un grupo por texto no resuelto (match exacto no genera grupo, se auto-asigna), con `<select>` para elegir entre *usar el sugerido*, *crear nuevo* o *elegir del catálogo* → *resultado* (igual que antes: creados/omitidos/errores por fila). ### Backend (Sprint 6 — Bases de conocimiento y niveles)

Salió del pedido de **clasificar las preguntas por tema y dificultad** (*"Gestión de residuos - Básico"*). El diagnóstico que ordenó todo el diseño: los módulos reales (`SIMA Básico`/`Intermedio`/`Avanzado`, `prisma/seed.ts`) **ya eran el eje dificultad**, con el tema disuelto adentro — o sea que no era agregar metadata, era **separar dos ejes que estaban colapsados en uno**.

- **`Etiqueta` se eliminó, no se extendió.** Cumplía la misma función pero como N a N de tags libres y opcionales, y estaba **muerta**: el seed no creaba ninguna, el import no asignaba y ningún frontend mandaba `etiquetaIds` (verificado con grep sobre los tres subproyectos, y con `SELECT count(*)` sobre las dos tablas antes de dropearlas: 0 filas). Lo único que se perdió es el eje **nominal** (agrupar por subtema además de por nivel); si reaparece, va una entidad nueva y deliberada, no revivir esa.
- **La base NO se versiona — es taxonomía, no contenido.** "Gestión de residuos" como materia es la misma en 2020 y en 2026; lo que cambia es qué se considera correcto adentro. Cuando sale un manual nuevo: papelera a las preguntas obsoletas, alta de las nuevas en la **misma** base, y versión nueva de los módulos que la evalúan — los dos mecanismos de versionado que ya existen alcanzan. Se descartó explícitamente **crear una base por manual** ("Gestión de Residuos 2026") porque parte las estadísticas justo en el eje que se quiere medir, y **versionar la base** porque obligaría a que los criterios de módulo apunten a una *versión* de base, con un pivot paralelo y tres entidades versionadas cruzándose. El año/revisión sale de `fuente`, nunca del nombre.
- **El nivel es ordinal y la escala es POR BASE**, por eso `NivelBase` es tabla y no enum: una base puede necesitar 3 niveles y otra 5. Un enum global impondría la misma escala a todas.
- **La coherencia base↔nivel la garantiza la base de datos, no el service.** `Pregunta` tiene dos FK: la simple a `BaseConocimiento` y una **compuesta** `(nivelId, baseConocimientoId)` → `NivelBase(id, baseConocimientoId)`. Para eso existe el `@@unique([id, baseConocimientoId])` de `NivelBase`, que no es una unicidad de negocio sino el requisito de Postgres para poder referenciar esas columnas. Se eligió esto sobre un `findFirst` previo en el service porque un chequeo en memoria no sobrevive a dos altas concurrentes. **Prisma acepta que `baseConocimientoId` participe en las dos relaciones** — se verificó con `prisma validate` y, sobre todo, en el SQL generado, que emite las dos FKs sin descartar ninguna.
- **Un CHECK escrito a mano tapa el agujero de MATCH SIMPLE.** Las FK compuestas de Postgres no se evalúan si *alguna* columna es NULL. Eso es deseado para `(base cargada, nivel NULL)` —"tema definido, dificultad pendiente" es un estado válido— pero dejaría pasar el inverso. De ahí `CHECK (nivel_id IS NULL OR base_conocimiento_id IS NOT NULL)`, que **vive sólo en el SQL de la migración**: Prisma no lo conoce ni lo introspecta, misma familia que los cinco índices únicos parciales del proyecto (ver `docs/pendientes.md`). Ojo que `ModuloVersionCriterio` (Sprint 7) tiene la misma FK compuesta pero **no** necesita este CHECK: ahí `baseConocimientoId` es NOT NULL, así que el caso "nivel sin base" no se puede dar.
- **Las tres constraints se verificaron con `INSERT` directo antes de escribir el service**: nivel de otra base → rechazado por la FK compuesta; nivel sin base → rechazado por el CHECK; base sin nivel → aceptado.
- **`baseConocimientoId` es nullable en base de datos pero obligatorio en el formulario.** El banco ya tenía preguntas cargadas y no hay forma de derivar la base del texto, así que un `NOT NULL` habría exigido inventar una base "sin clasificar" para todas. El filtro `?sinBase=true` es lo que permite ir limpiando ese backlog.
- **`Pregunta.fuente` se congela al crear.** Se copia de la `fuente` de la base si el alta no trae una propia (`resolverFuente`). Sin esto, actualizar la fuente de la base al salir un manual nuevo haría que las preguntas viejas —las que ese manual dejó obsoletas— pasen a citar el manual nuevo. Verificado end-to-end: cambiar la base a `Rev. 4` deja las preguntas previas en `Rev. 3` y sólo las nuevas toman la `Rev. 4`.
- **Reordenar la escala se hace reindexando TODO, en dos pasadas.** El índice `(base_conocimiento_id, orden)` **no es diferible**, así que mover niveles de a uno lo viola a mitad de camino aunque estén en la misma transacción — mismo problema que el `principal` de `VinculacionPuestoCentro`. `PUT /:id/niveles/orden` recibe la escala completa y, en una transacción: (1) toda la escala a negativos, (2) cada nivel a su posición final. Los rangos de valores nunca se solapan, así que no hay colisión. Se eligió sobre el intercambio a tres UPDATEs porque ese sólo cubre *swaps* y se rompe al mover un nivel a una posición arbitraria. Confirmado contra Postgres que el enfoque ingenuo **sí** falla (`duplicate key value violates unique constraint`) y que el endpoint hace el mismo movimiento sin romperse.
  - ⚠️ **La pasada 1 va en `tx.$executeRaw`**: `orden = -orden - 1` referencia la propia columna y el `data` de Prisma sólo acepta literales o sus operaciones atómicas (`increment`/`decrement`/`multiply`/`set`) — ninguna combinación lo expresa. La pasada 2 sí es Prisma normal (cada fila recibe un literal distinto).
  - Por eso `PATCH /:id/niveles/:nivelId` **sólo renombra**: no hay una segunda vía para tocar `orden`.
  - **`orden` es ordinal, NO contiguo — y eliminar un nivel deja un hueco a propósito.** Borrar el nivel del medio de `0,1,2` deja `0,2`: la unicidad se mantiene y el orden relativo no cambia, que es lo único que `orden` significa. `eliminarNivel` **no reindexa** porque renumerar en cada borrado costaría una transacción con SQL crudo para un beneficio cosmético; `reordenarNiveles` es lo único que renumera, y de paso normaliza los huecos. Consecuencia a tener presente: `siguienteOrden` usa `max(orden) + 1`, así que borrar y agregar repetido hace subir los números sin que vuelvan a bajar. Hay un spec que fija esta decisión para que no se "arregle" sola.
- **El rechazo de la base de datos se traduce a 400, no se deja salir como 500.** La FK llega como `PrismaClientKnownRequestError` con código `P2003`; el CHECK, en cambio, llega como `PrismaClientUnknownRequestError` **sin código de Prisma** (es un error crudo de Postgres, `23514`), así que se identifica por el nombre de la constraint. Se detectó porque la primera corrida de la verificación end-to-end devolvía 500 en los dos casos.
- **El import de Excel no necesitó cambios.** `ConfirmarImportPreguntasDto.preguntas` es `CreatePreguntaDto[]` y `confirmarPreguntas` pasa cada fila entera a `PreguntasService.create`, así que la clasificación viaja **dentro de cada pregunta**. El modal estampa la base/nivel elegidos en cada fila; el `fuente` lo autocompleta el backend. Verificado con un `.xlsx` real de punta a punta.
- **La Entrega B ya está implementada** (composición de módulos por criterio) — ver Sprint 7, abajo. Lo que sigue diferido de esta feature son las **estadísticas por base** (`Evaluacion` + `RespuestaEvaluacion`), que son su objetivo declarado pero dependen de conectar la app tablet.

### Backend (Sprint 7 — Composición de módulos por criterio)

Es la **Entrega B** de bases de conocimiento. Hasta acá una `ModuloVersion` se armaba enumerando preguntas una por una; ahora puede además declarar **qué evalúa** (`ModuloVersionCriterio`: base + nivel opcional) y dejar que el backend materialice el pool.

- **`cantidadPreguntas` se sacó del diseño original** (decisión del 2026-08-03). Iba a ser cuántas preguntas sortear por examen de cada criterio, pero **no tiene consumidor**: la tablet sortea 3 fijas con `pickRandomQuestions` y no lee nada del backend. Guardarlo ahora lo dejaba exactamente en la situación de `Modulo.vigenciaMeses` — un campo que se persiste, aparece en formularios y no gobierna ninguna regla. Se agrega como columna nullable, sin backfill, cuando exista el sorteo real. Lo que se pierde mientras tanto es la garantía de cobertura por criterio (tomar N del pozo unificado puede dar 3 de residuos y 0 de altura), que es un problema **del sorteo** y no de la composición: la clasificación de cada `Pregunta` alcanza para reintroducir la cuota sin remodelar nada.
- **El pool materializa TODAS las preguntas que matchean**, no una muestra: congelar unas pocas haría que todos los alumnos rindan exactamente las mismas y se pierde la aleatorización.
- **Snapshot, no receta viva.** `PUT /:id/criterios` materializa los pivots sobre el BORRADOR y `activar()` los publica **sin volver a resolver** (hay un spec que lo fija). Resolver al rendir dejaría a una versión `ARCHIVADO` como puntero a un pozo que se mueve por debajo, y no se podría reconstruir qué se pudo tomar en una fecha — que es todo el motivo del versionado del Sprint 3. **Costo aceptado y verificado**: una pregunta cargada después de publicar no entra sola ni a la versión publicada ni al borrador que se cree a partir de ella; entra recién cuando el admin vuelve a guardar los criterios.
- **La resolución es un UPSERT, no un replace**, y ahí está toda la sutileza:

  | Caso | Acción |
  |---|---|
  | Matchea y ya tiene pivot `CRITERIO` | **No se toca** — preserva un `activa: false` puesto a mano, y hace la resolución idempotente |
  | Matchea y no tiene ningún pivot | Se inserta `origen: CRITERIO`, `activa: true`, `orden = max+1` |
  | Pivot `CRITERIO` que ya no matchea | **Se borra**, esté activo o desactivado |
  | Pivot `MANUAL` | **Nunca se toca** (misma regla que `recalcular()` con las `Asignacion` MANUAL) |

  El pivot `CRITERIO` huérfano **se borra aunque estuviera desactivado a mano** porque es estado derivado: sacado el criterio se queda sin ninguna razón de estar, y desactivado sería una fila invisible-pero-presente que alguien puede reactivar sin nada que la respalde. Se descartó **promoverlo a `MANUAL`**: reescribe el origen en silencio y deja sin respuesta "¿qué trajo el criterio?". Si la pregunta igual importa, se vuelve a agregar desde el banco y queda `MANUAL`, que es la verdad. Una pregunta que **ya es `MANUAL`** y además matchea un criterio conserva su origen: no se puede tener dos filas (la PK es (versión, pregunta)) y pisarle el origen sería justamente tocar una MANUAL.
- **El pool sólo toma preguntas con `activa: true`**, y es **literalmente el mismo filtro que `GET /preguntas?baseId=&nivelId=&activa=true`** — a propósito: el backoffice previsualiza el conteo con ese endpoint y por eso no hizo falta uno de dry-run. Corolario: mandar una pregunta a papelera la saca del pool y la resolución siguiente **borra** su pivot `CRITERIO`; recuperarla no la devuelve sola al módulo, pero la resolución siguiente sí.
- **Un criterio que matchea CERO preguntas se guarda igual**, con el conteo en 0 y un badge ámbar. Declarar el tema antes de cargar las preguntas es un flujo válido, y rechazarlo obligaría a cargar preguntas para poder declarar qué se evalúa. Tampoco bloquea Activar: publicar un módulo sin preguntas ya era posible.
- **Unicidad: `@@unique` de Prisma MÁS un índice parcial a mano.** El `@@unique([moduloVersionId, baseConocimientoId, nivelId])` cubre sólo la mitad `nivel_id NOT NULL` (en Postgres dos NULL nunca colisionan, así que no impide declarar dos veces "cualquier nivel de esta base"); la otra mitad la cubre `modulo_version_criterio_base_sin_nivel` (`WHERE nivel_id IS NULL`), el **quinto** índice parcial invisible para Prisma. A diferencia de `ReglaAsignacion` —que dropeó su `@@unique` entero porque `deleted_at` atraviesa los dos alcances— acá no hay soft-delete y el `@@unique` plano se conserva. Las cuatro combinaciones (nivel de otra base, dos "cualquier nivel", dos niveles distintos, el mismo dos veces) se verificaron con `INSERT` directo antes de escribir el service: son constraints que ningún spec con Prisma mockeado puede ejercitar.
- **`unassignPregunta` rechaza con 409 los pivots `CRITERIO`.** Quitarla a mano no sirve: la resolución siguiente la vuelve a materializar. El mensaje dice que la vía es **"Desactivar"** y —lo que importa— que **esa baja sobrevive a las resoluciones siguientes**; sin esa segunda mitad, alguien que quiere sacar UNA pregunta termina borrando el criterio entero y se lleva puestas todas las demás. Hay un spec que fija las dos partes del mensaje con regex.

**Frontend — `CriteriosPanel.jsx` y su convivencia con el staging.** La sección vive dentro del editor de contenido de `TrainingModules.jsx`: editable en el BORRADOR, de solo lectura en la vigente publicada y en el detalle del historial. Selects **encadenados** de base y nivel (mismo patrón y mismo motivo que el filtro de `Questions.jsx`: un nivel sólo existe dentro de su base), opción "Cualquier nivel", conteo en vivo por fila y marca del criterio repetido en la fila que sobra.

- **Tiene su propio botón "Guardar criterios", que pega al backend al toque** — a diferencia del resto del editor, que es staged (`localAsignadas` + `flushCambios`). Que convivan dos modelos de guardado es tolerable **si el usuario los ve**: el modal de confirmación dice que esto se guarda ahora mismo y, si hay N cambios de preguntas sin guardar, avisa que se guardan junto con los criterios. `flushCambios()` nunca corre sin que eso esté escrito.
- **El guardado es de tres pasos y termina en un re-baseline.** El `PUT` materializa pivots **en el servidor**, así que después las dos fotos del staging quedan viejas: `banco.asignadas` (la base del diff) y `localAsignadas` (lo editado). Refrescar sólo `banco` sería **peor que no hacer nada** — el `flushCambios` siguiente vería los pivots recién materializados en `antes` pero no en `ahora` y los borraría. Por eso: (1) `flushCambios()`, (2) `PUT`, (3) `sessionKeyRef.current = null` + `banco.refresh()`, que hace que el efecto de staging vuelva a correr y re-snapshotee las dos fotos desde el servidor. Sin maquinaria nueva: `banco.version` ya estaba en las deps del efecto.
- **El paso 3 va en `finally`, no en el camino feliz.** Si el flush se aplica y el `PUT` falla (409 porque otra sesión publicó la versión, un corte de red), el servidor ya tiene los cambios de preguntas y `banco.asignadas` no — el flush siguiente intentaría des-asignar un pivot que ya no existe y moriría con un 404. Resincronizar siempre cuesta perder las filas de criterios que se estaban editando, y a cambio deja la sesión consistente; el mensaje de error lo dice. Por eso el error se muestra **en el panel y no en el modal**: el modal se cierra y el contenido se recarga, así que el mensaje tiene que estar al lado de los criterios ya resincronizados.
- **El conteo total es UNIÓN, no suma.** Dos criterios pueden pisarse ("cualquier nivel de Seguridad" + "Seguridad-Básico") y el backend los unifica en un `Set`; sumar los conteos por fila daría un total que no coincide con los pivots resultantes. Por eso el panel guarda los **ids** que devuelve `GET /preguntas`, no el `length`.
- En `PreguntasAsignadasPanel`, las filas con `origen: CRITERIO` llevan badge indigo **"Por criterio"** y **no ofrecen "Quitar"** (queda "Desactivar"). El 409 del backend es el backstop, no la primera línea de defensa.
- `claveCriterio` (la identidad `base::nivel ?? '*'`, que hace colisionar nivel ausente con `null`) vive en `bancoModulo.jsx` y no en el componente, por `react-refresh/only-export-components` — que es la razón por la que ese archivo existe.

## Cómo agregar un producto futuro (ej: SIMA INSPECTIONS)

1. Crear `src/sima-inspections/data/` con sus entidades.
2. Crear `src/sima-inspections/pages/` con sus pantallas (incluyendo un `Overview.jsx`).
3. Agregar el producto al sidebar en `BackofficeLayout.jsx`:
   - Nuevo ítem en la sección "Productos"
   - Nuevo Set equivalente a `SIMA_CHECK_PAGES` y array de tabs
4. Registrar las páginas nuevas en `PAGES` de `App.jsx`.
5. Agregar una product card en `Dashboard.jsx`.

No hay excepciones a esta convención: `ReglasAsignacion.jsx` era la única (vivía en `core/pages/` siendo un tab de SIMA CHECK) y ya se movió a `sima-check/pages/`.
