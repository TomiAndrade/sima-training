# TRAINING — SIMA TRAINING Platform

## Qué es esto

MVP de alta fidelidad para validar la plataforma **SIMA TRAINING** de **Ingeniería Sima** ante clientes de la industria Oil & Gas. Nació como demo navegable solo-frontend (datos mockeados) y desde el **Sprint 1** tiene un **backend real** (NestJS + PostgreSQL). Hoy el backoffice persiste contra base de datos en casi todas sus pantallas y **la app tablet también está conectada**: rinde contra `/tablet/*` y el resultado lo calcula el backend.

**SIMA CHECK** (capacitaciones y evaluaciones industriales) es el primer producto integrado en la plataforma. La arquitectura está preparada para incorporar productos futuros (SIMA INSPECTIONS, SIMA AUDITS, etc.) sin reorganizaciones.

## Tres proyectos independientes

| Proyecto | Descripción | Puerto dev |
|---|---|---|
| `sima-training-api/` | **Backend** NestJS + PostgreSQL + Prisma (Sprint 1) | 3000 |
| `sima-training-backoffice/` | Backoffice de la plataforma SIMA TRAINING | 5173 |
| `sima-check-app/` | App de evaluación para tablets industriales (producto SIMA CHECK) | 5174 |

## Stack técnico

**Frontends** (`sima-training-backoffice`, `sima-check-app`):
- **Vite + React** (template react)
- **Tailwind CSS v3** + PostCSS + Autoprefixer
- Sin router (navegación con `useState`)

**Backend** (`sima-training-api`):
- **NestJS 11** + TypeScript (monolito modular por dominio)
- **PostgreSQL 16** (local vía Docker Compose)
- **Prisma 6** (ORM + migraciones)
- **JWT** para auth básica (sin roles todavía)

> El backoffice ya consume la API real (ver `src/core/api/`) en **Usuarios, Puestos, Centros de Costo, Módulos, Preguntas, Reglas de asignación, Asignaciones y el Resumen de SIMA CHECK**. Siguen mockeadas **Dashboard y Clientes**; se migran ABM por ABM en sprints siguientes. La app tablet (`sima-check-app`) **ya está conectada**: consume `/tablet/*` vía `src/core/api/` y no le queda ningún mock de datos (`src/data/` se eliminó). Lo que sigue pendiente ahí es el **offline de datos**, no la conexión.

## Cómo correr

Detalle completo del backend en [`sima-training-api/README.md`](sima-training-api/README.md).

```bash
# 1. Backend (requiere Docker Desktop corriendo)
cd TRAINING/sima-training-api
npm install
cp .env.example .env
docker compose up -d db          # PostgreSQL local
npx prisma migrate dev           # crea las tablas
npx prisma db seed               # organización interna (nada más)
npm run start:dev                # → http://localhost:3000

# 2. Backoffice
cd TRAINING/sima-training-backoffice
npm install
cp .env.example .env             # VITE_API_URL apunta al backend local
npm run dev                      # → http://localhost:5173

# 3. App tablet (consume el backend: necesita la API corriendo)
cd TRAINING/sima-check-app
npm install
npm run dev                      # → http://localhost:5174
```

### Contenido de SIMA CHECK (`SEED_SIMA_CHECK=true`)

`prisma/seed.ts` tiene dos modos. El **seed base** (el `npx prisma db seed` de arriba) siembra sólo la estructura mínima que necesita cualquier entorno: la organización interna "Ingeniería SIMA", y nada más. Detrás de `SEED_SIMA_CHECK=true` se suma el **contenido real de evaluación** (`sembrarSimaCheck()`), apagado por defecto a propósito porque es contenido, no estructura.

**El seed base no siembra módulos.** Sembraba cuatro (`SIMA Básico`/`Intermedio`/`Avanzado`/`Reglas de Oro`) con **uuid fijo**, que eran la contraparte real del mock `sima-check/data/training-modules.js` de cuando el backoffice lo referenciaba por `backendId`. Ese campo ya no existe —la pantalla Módulos es 100% backend— así que los cuatro quedaron como filas vacías apareciendo al lado de cualquier módulo creado de verdad. **Un módulo es contenido, no estructura**: lo crea quien lo necesita — la segunda rama del seed los cinco reales, y el admin los suyos desde el backoffice.

```powershell
# PowerShell
$env:SEED_SIMA_CHECK='true'; npx prisma db seed
```
```bash
# bash
SEED_SIMA_CHECK=true npx prisma db seed
```

Qué siembra:

| | |
|---|---|
| **Catálogos** | Los **88 puestos** de la hoja "Listado de Puestos" y los **16 centros de costo** (los valores distintos de "Dependencia" en la nómina). Se **reusan por nombre** si ya existen (`resolverCatalogo`) y **nunca se borran** |
| **Bases de conocimiento** | Tres: `[IND] Inducción SSMAC Ingeniería Sima` con escala `Básico`/`Intermedio`/`Avanzado`, `[ORO] Reglas de Oro Industria Petrolera` y `[RSV] Reglas que Salvan Vidas — Phoenix`, las dos últimas con un solo nivel `General`. Los niveles se crean sin `orden` explícito, para ejercitar el appendeo |
| **Banco** | **202 preguntas** con **73 imágenes**: 92 Verdadero/Falso, 65 de opción múltiple y 45 de opciones con imagen. Todas clasificadas — acá no queda backlog "sin clasificar" |
| **Módulos** | Los **cinco**, publicados en `2026.01.00`. Cada uno se llena **por un solo criterio** (base + nivel), o sea 100% pivots `origen: CRITERIO`: `SIMA Básico` 63, `SIMA Intermedio` 26, `SIMA Avanzado` 33, `Reglas de Oro Industria Petrolera` 27 y `Reglas que Salvan Vidas — Phoenix` 53 |
| **Reglas** | **54**, escalonadas por jerarquía y con los **dos alcances**: de centro (Básico a los 16 centros, Reglas de Oro a los 14 operativos, Intermedio a los 4 de obra/taller/logística, Phoenix a S31 y S49) y de par exacto (Avanzado a 9 puestos de conducción en las 2 estructuras) |
| **Personas** | **Ninguna.** La nómina es PII y no vive en ningún archivo versionado: se importa desde el backoffice contra "Ingeniería SIMA". Mientras no haya usuarios las reglas no derivan ninguna `Asignacion`; se materializan solas al importarlos |

Qué mostrar de esto: los `preguntasPorExamen` (12–15 según el módulo) son **mucho menores que el pool**, así que dos personas del mismo puesto no rinden el mismo examen y un reintento tampoco repite las mismas preguntas. **El reparto de reglas es una propuesta, no un dato**: los Excel no dicen qué puesto rinde qué módulo, y se edita desde el backoffice sin tocar el seed.

`sembrarSimaCheck()` **reusa los services de Nest** (levanta un application context con `NestFactory.createApplicationContext`) en vez de escribir inserts crudos, para no saltearse las reglas que viven en ellos: `resolverFuente`, el appendeo de `orden`, la validación de que la `respuestaCorrecta` esté entre las opciones, la resolución de criterios y el cálculo del número `AÑO.MAYOR.MENOR`. Lo único que no corre por esa vía es la `ValidationPipe` global, que vive en `main.ts` y sólo aplica a la capa HTTP.

**Las imágenes se suben por `StorageService`**, no se copian a `./uploads`: así el seed corre igual con el driver `local` y con `r2` (el deploy no tiene disco). Y `limpiarSimaCheck()` las **borra del storage antes** de borrar las preguntas, porque lo único que dice dónde están son las columnas que el borrado va a eliminar — sin eso cada corrida dejaría 73 archivos huérfanos más. Ver [decisiones/infraestructura.md](docs/decisiones/infraestructura.md).

#### De dónde sale ese contenido

De los **cinco Excel** con los que se venían tomando las evaluaciones en papel, que están en `docs/` y **no se versionan** (el `.gitignore` bloquea `docs/*.xlsx` porque el archivo hermano de nómina lleva PII). Lo versionado es la salida: `prisma/seed-data/preguntas-sima-check.ts`, `prisma/seed-data/catalogos-nomina.ts` y las imágenes de `prisma/seed-assets/preguntas/` — **archivos generados, no se editan a mano**.

Los genera [`scripts/contenido/`](scripts/contenido/README.md) (Python + openpyxl + Pillow; hace falta leer el relleno de las celdas, la capa de drawing y los recortes `srcRect`, y `exceljs` no expone la capa de drawing). La convención central del Excel es que **la respuesta correcta está pintada de verde**, y en dos lugares distintos según si la opción es texto o imagen; eso, los tres casos que el Excel deja ambiguos y por qué se resolvieron así están en [decisiones/preguntas.md](docs/decisiones/preguntas.md).

⚠️ **No confundir con `sima-training-api/scripts/demo/`**, que es otra cosa: un banco inventado y unos Excel generados para mostrar en vivo el flujo de import con sus badges de similitud.

## Backend — `sima-training-api` (Sprint 1)

Monolito NestJS organizado por dominio. Detalle en [`sima-training-api/README.md`](sima-training-api/README.md).

### Entidades reales (Prisma — `prisma/schema.prisma`)

| Entidad | Campos clave |
|---|---|
| `Usuario` | `id, nombre, apellido, dni` (único), `email?` + trazabilidad + `deletedAt` (soft-delete). **Identidad pura**: no tiene rol, ni organización, ni clasificación (ver `Vinculacion`) |
| `Vinculacion` | `id, usuarioId` (**único** — una vinculación por usuario), `organizacionId` (FK), `rol` (ADMINISTRADOR/COORDINADOR/**AUDITOR**/ALUMNO), `activa` + trazabilidad + `deletedAt`. Es donde viven organización y rol desde el modelo de vinculación |
| `VinculacionPuestoCentro` | PK `[vinculacionId, puestoId, centroCostoId]` (los tres NOT NULL), `principal` (solo display), `activo` (baja lógica). Un **par** (puesto, centro de costo) que la persona ejerce. Una vinculación puede tener **cero, uno o varios** pares |
| `Puesto` / `CentroCosto` | `id (uuid), nombre` (único), `activo` + trazabilidad — catálogos de nómina |
| `Organizacion` | `id, nombre, tipo` (CLIENTE/SUBCONTRATISTA/**INTERNA**), `organizacionPadreId` (FK self-referencial), `activa` + trazabilidad |
| `Pregunta` | `id (uuid), texto, tipo` (VERDADERO_FALSO/OPCION_MULTIPLE/OPCIONES_IMAGEN/TEXTO_LIBRE), `opciones?` (jsonb: array de strings — texto en OPCION_MULTIPLE, **claves de storage** en OPCIONES_IMAGEN), `respuestaCorrecta?` (el string exacto de una de las opciones; el backend lo valida), `imagen?, puntajeMax?, activa` + trazabilidad. Única: se comparte entre módulos, nunca se duplica. `imagen` es la **imagen del enunciado**: guarda una **clave opaca** de storage (`preguntas/<uuid>.png`, se sirve bajo `/uploads`) o una ruta legacy relativa a `public/` si vino del import de Excel. Se setea solo al crear y es **inmutable** (ver [decisiones/preguntas.md](docs/decisiones/preguntas.md)). **Clasificación**: `baseConocimientoId?`, `nivelId?` y `fuente?` — nullable en base de datos pero obligatoria la base en el formulario de alta (ver [decisiones/preguntas.md](docs/decisiones/preguntas.md)) |
| `BaseConocimiento` | `id (uuid), nombre` (único), `codigo?` (único), `descripcion?` (qué entra y qué no), `fuente?` (de qué manual sale el temario **hoy**), `color?, orden?, activa` + trazabilidad. El **tema** de una pregunta. **No se versiona**: es taxonomía, no contenido (ver [decisiones/preguntas.md](docs/decisiones/preguntas.md)) |
| `NivelBase` | `id (uuid), baseConocimientoId, nombre, orden` + trazabilidad. La escala **ordinal** de dificultad de una base. Es tabla y no enum porque **la escala es por base**: una puede tener 3 niveles y otra 5. Únicos `[base, nombre]`, `[base, orden]` y `[id, base]` — este último no es unicidad de negocio, habilita la FK compuesta de `Pregunta` |
| `Modulo` | `id (uuid), nombre, descripcion?`, `activo` (baja lógica del módulo entero, **independiente** del ciclo BORRADOR/ACTIVO/ARCHIVADO de sus versiones: el admin lo retira/reactiva a mano), `vigenciaMeses?` + trazabilidad. Contenedor estable; el contenido real vive en `ModuloVersion`. `vigenciaMeses` gobierna el vencimiento de las aprobaciones (ver [decisiones/asignaciones.md](docs/decisiones/asignaciones.md)): `null` = no vence nunca, el default de todos los módulos cargados hoy |
| `ModuloVersion` | `id (uuid), moduloId, numeroVersion` (contador interno monotónico), `estado` (BORRADOR/ACTIVO/ARCHIVADO), `anio?/mayor?/menor?` (número público `AÑO.MAYOR.MENOR`, se asigna al Activar), `activadaEn?` (timestamp de publicación), `esNuevaLinea?` (elección guardada en el borrador: true = sube MAYOR, false = sube MENOR) + trazabilidad. Editar un módulo activo crea una versión nueva (borrador); al activarla la anterior queda `ARCHIVADO` e inmutable. **Parámetros de examen** (los cuatro `Int?`): `preguntasPorExamen`, `umbralAprobacion` (en %), `maxIntentos` y `esperaEntreIntentosMinutos` — **`null` = usar el default global** (3 / 70% / sin tope / sin espera), nunca cero. Viven en la versión y no en `Modulo` porque se congelan con ella: sólo se editan en BORRADOR (`PUT /modulos/:id/parametros`, 409 sobre lo publicado) y `crearVersion()` los copia del ACTIVO. Ver [decisiones/modulos.md](docs/decisiones/modulos.md) |
| `ModuloVersionPregunta` | Pivot `ModuloVersion` ↔ `Pregunta`. PK `[moduloVersionId, preguntaId]`, `orden`, `obligatoria`, `activa` (baja lógica **por módulo**) y **`origen`** (`CRITERIO`/`MANUAL`, default MANUAL). El `origen` es lo que permite que la resolución de criterios sepa qué filas le pertenecen: crea y borra sólo las `CRITERIO` y **nunca toca las `MANUAL`** (ver [decisiones/modulos.md](docs/decisiones/modulos.md)) |
| `ModuloVersionCriterio` | `id (uuid), moduloVersionId, baseConocimientoId` (**NOT NULL**), `nivelId?` (null = cualquier nivel de esa base) + trazabilidad. **Qué evalúa** una versión, declarado por tema en vez de enumerando preguntas. Una versión puede declarar varios niveles de la misma base (son criterios distintos). **No guarda cuántas preguntas sortear** — ver [decisiones/modulos.md](docs/decisiones/modulos.md). FK compuesta `(nivelId, baseConocimientoId)` → `NivelBase(id, baseConocimientoId)`, igual que `Pregunta`; unicidad con `@@unique` **más** un índice parcial `WHERE nivel_id IS NULL` |
| `ReglaAsignacion` | `id (uuid), puestoId?, centroCostoId, moduloId` (`puestoId` nullable), `activo`, `deletedAt` + trazabilidad. **Dos alcances que conviven**: con `puestoId` es una regla por **par exacto** (puesto, centro de costo); con `puestoId` en **null** es una regla de **centro de costo**, que aplica a todos los puestos de ese centro. Un soldador de Taller alcanzado por las dos recibe los dos módulos — `recalcular()` los unifica en un único `Set` de módulos requeridos, nunca duplica la `Asignacion`. Apunta a `Modulo` (el contenedor), no a una `ModuloVersion` — la obligación es "este módulo", la versión concreta se resuelve al rendir. **Dos ejes de baja independientes**: `activo` es la pausa reversible (sigue listada y se reactiva), `deletedAt` es la eliminación (deja de listarse y de matchear). Volver a crear el mismo triple **revive la misma fila** en cualquiera de los dos casos, nunca duplica. **La unicidad se cubre con dos índices parciales y ningún `@@unique`** (ver abajo) |
| `Asignacion` | `id (uuid), usuarioId, moduloId, moduloVersionId?`, `origen` (AUTOMATICA/MANUAL), `revocadaAt?` + trazabilidad. Obligación concreta de una persona de rendir un módulo. **Nunca se borra, se revoca.** Índice único parcial `WHERE revocada_at IS NULL` → a lo sumo una vigente por (usuario, módulo). **`moduloVersionId` significa "con qué versión se CUMPLIÓ"**: lo completa `SesionesService.registrar()` **sólo al aprobar** (un intento desaprobado no lo toca; una aprobación posterior sobre una versión más nueva lo pisa), y `null` = todavía no se cumplió. No es "la última versión rendida" — eso ya lo guarda cada `Sesion` por intento. Aprobar **no revoca** la asignación: sigue vigente porque la regla la sigue pidiendo, y "pendiente" pasa a ser *vigente sin aprobación* (ver [decisiones/sesiones.md](docs/decisiones/sesiones.md)) |
| `Sesion` | `id (uuid), usuarioId, moduloVersionId` (**NOT NULL**), `asignacionId?`, `iniciadaEn/finalizadaEn`, `correctas, total, porcentaje, umbralAprobacion, aprobada` + `createdAt/createdBy`. **Un intento** de rendición. Apunta a la **versión** y no al módulo: un score sólo significa algo contra el set de preguntas publicado en ese momento. **Inmutable** (sin `updatedAt`, sin soft-delete) y **sin unicidad** sobre (usuario, versión): un reintento es una fila más. Ver Sprint 8 |
| `Respuesta` | `id (uuid), sesionId, preguntaId, respuestaDada?` (null = no contestó), `correcta` + `createdAt`. Una por pregunta contestada. `@@unique([sesionId, preguntaId])` — plano, Prisma lo conoce, **no** es un sexto índice parcial. **No desnormaliza base/nivel**: las estadísticas por base salen por join `Respuesta → Pregunta → BaseConocimiento` (ver la advertencia de `docs/pendientes.md` antes de agregar un endpoint que reclasifique preguntas) |
| `AuditLog` | `id (uuid), entidad, entidadId` (String, **sin FK** — ver más abajo), `accion` (CREATE/UPDATE/DELETE), `diff` (jsonb `{ campo: { antes, despues } }`, sólo lo que cambió), `actor` (String libre) + `createdAt`. Log de auditoría (Story 9): **inmutable, sin soft-delete** — es un hecho histórico, borrarlo (aunque sea lógicamente) le pega al propósito de la tabla. Hoy sólo audita `Vinculacion` y `VinculacionPuestoCentro`; el resto de las entidades queda sin cubrir a propósito (ver `docs/pendientes.md`) |

**Tipo `INTERNA`:** La organización **"Ingeniería SIMA"** usa este tipo. Los usuarios que pertenecen a ella son usuarios internos de SIMA (administradores del sistema); el resto (CLIENTE/SUBCONTRATISTA) son usuarios de clientes.

**Decisión clave — `Usuario` es UNA sola entidad** para cualquier persona (cuenta de sistema y/o persona evaluada). Esto unifica los conceptos `User` y `Employee` que el prototipo modelaba por separado. `rol = ALUMNO` es la persona evaluada (equivalente al `Employee`/"Empleado" del modelo de roles); ADMINISTRADOR/COORDINADOR son las cuentas de sistema del backoffice, y AUDITOR es el rol de las organizaciones CLIENTE. **El rol ya no vive en `Usuario`: vive en `Vinculacion`** (ver abajo).

**Modelo de vinculación:** `Usuario` quedó como **identidad pura** (nombre, apellido, DNI, email). Todo lo que es pertenencia se movió a `Vinculacion` — **una por usuario**, con **organización y rol** —, y el par **puesto + centro de costo** vive en `VinculacionPuestoCentro`, una fila por par completo (los tres campos de la PK son NOT NULL: nunca un puesto sin centro ni al revés).

- Una persona puede tener **varios pares**, y el mismo puesto en dos centros son **dos pares distintos** ("Soldador en YPF" ≠ "Soldador en PAE"): la capacitación obligatoria depende del par, no de dos listas sueltas.
- **Regla de negocio: el alumno hace los módulos de TODOS sus pares**, no solo del principal.
- **`principal` es solo display** — qué par se muestra en la fila del listado. No interviene en ninguna regla de capacitación. Manejo mínimo a propósito: el primer par que se carga queda principal, y no hay herencia automática si después se desactiva (que se muestre un par inactivo es cosmético, no un bug). Si alguna vez hace falta hacer un swap de principal, va en **dos UPDATEs dentro de una transacción** (bajar el viejo, subir el nuevo): el índice único parcial `UNIQUE (vinculacion_id) WHERE principal AND activo` no es diferible y un `updateMany` único lo viola a mitad de camino.
- Cero pares es una cardinalidad válida (el pivote arranca vacío): el listado **no oculta** a esas personas.

**Clasificación (SIMA/CLIENTE/SUBCONTRATISTA/INVITADO): se disolvió como concepto.** Ya no se persiste en ningún lado — la pertenencia se **deriva** de `Organizacion.tipo` (INTERNA/CLIENTE/SUBCONTRATISTA) más la cadena de `organizacionPadreId` ("para quién trabaja" un subcontratista). `INVITADO` quedó fuera del modelo, a definir cuando se implemente el acceso de única vez.

**Matriz tipo-de-organización ↔ rol:** `INTERNA` → todos (ADMINISTRADOR/COORDINADOR/AUDITOR/ALUMNO) · `CLIENTE` → solo AUDITOR · `SUBCONTRATISTA` → solo ALUMNO. Vive en `src/usuarios/matriz-rol-organizacion.ts` y se valida **en el service** (cruza dos tablas — rol en `Vinculacion`, tipo en `Organizacion` — así que no hay CHECK constraint posible, y tampoco puede ir en el DTO). Corre en el alta/edición manual **y en el import de Excel**, que delega en el mismo `UsuariosService.create` en vez de tener su propia copia.

**Composición por criterio (Sprint 7):** el contenido de una versión se puede armar de dos formas que **conviven**: eligiendo preguntas a mano del banco (pivot `origen: MANUAL`, lo de siempre) o declarando **criterios** (`ModuloVersionCriterio`: base + nivel opcional) que materializan el pool de preguntas que matchean (pivot `origen: CRITERIO`). Es un **snapshot**, no una receta viva: el pool se materializa al guardar los criterios sobre un BORRADOR y `activar()` lo congela sin volver a resolver. Detalle completo en [decisiones/modulos.md](docs/decisiones/modulos.md).

**Banco de preguntas y módulos versionados (SIMA CHECK):** `Pregunta` es única y reutilizable entre módulos vía el pivot `ModuloVersionPregunta` (N a N). `Modulo` nunca se edita en el lugar: cambiar su contenido crea una `ModuloVersion` nueva y la anterior queda archivada e inmutable — no se pierden versiones viejas. Los tipos de pregunta (`VERDADERO_FALSO`/`OPCION_MULTIPLE`/`OPCIONES_IMAGEN`) mapean 1:1 a los tipos del mock frontend (`truefalse`/`multiple`/`image-options`); `TEXTO_LIBRE` está en el enum para uso futuro, sin implementación todavía.

**Clasificación del banco (Sprint 6):** cada `Pregunta` apunta a una **`BaseConocimiento`** (el tema — "Gestión de residuos") y, opcionalmente, a un **`NivelBase`** de esa base (la dificultad). Reemplaza a la vieja `Etiqueta`, que era un N a N de tags libres y estaba **muerta** (nadie la creaba ni la asignaba); se eliminó del todo en el mismo sprint. Motivación: los módulos reales (`SIMA Básico`/`Intermedio`/`Avanzado`) **codificaban la dificultad en el nombre** y disolvían el tema adentro — los dos ejes estaban colapsados en uno. Detalle completo en [decisiones/preguntas.md](docs/decisiones/preguntas.md).

**Baja lógica de preguntas por módulo:** una pregunta **no se edita, se activa/desactiva**. El pivot `ModuloVersionPregunta` tiene un flag `activa` (default `true`) que es la baja lógica **por módulo**: desactivar una pregunta la saca solo de ese módulo (togglea el flag en la versión vigente, in place — no crea versión nueva). Es distinto de `Pregunta.activa`, que es el flag global del banco. `GET /modulos/:id` devuelve todas las preguntas del módulo (activas e inactivas) para poder reactivarlas desde el backoffice.

**Papelera global de preguntas (distinta de la baja por módulo):** `Pregunta.activa` es un segundo flag, independiente del anterior — "enviar a papelera" (`PATCH /preguntas/:id { activa: false }`) saca la pregunta de **todo** el banco y cascadea `activa=false` a **todas** sus filas de `ModuloVersionPregunta` (cualquier módulo donde estuviera). "Recuperar" (`activa: true`) revierte el flag global pero **no** restaura los pivots por módulo — asimetría a propósito, para no adivinar en qué módulos el admin la quiere de vuelta. `GET /preguntas` soporta filtrar por `?activa=`, por `?moduloId=` (repetible, combina como OR entre módulos), y por `?sinAsignar=true` (preguntas sin ninguna asignación vigente, también OR con `moduloId`); cada pregunta devuelta trae `modulos: [{moduloId, moduloNombre, activaEnModulo}]` con sus asignaciones actuales.

**Detección de duplicados/similares (resuelto, en memoria):** `src/import/similitud.ts` normaliza el texto en español (sin acentos/puntuación) y compara por coeficiente de Dice sobre trigramas de caracteres, contra el banco completo y contra las filas del mismo archivo importado. Se eligió esta vía en vez de la extensión `pg_trgm` de Postgres porque el proyecto es local-first sin deploy cloud activo todavía; queda encapsulado en funciones puras, reemplazable el día que el banco crezca lo suficiente como para justificar un índice en base. Solo corre en el preview del import — el alta directa (`POST /preguntas`) no la ejecuta.

**Asignaciones automáticas por par (puesto, centro) → módulo:** `ReglaAsignacion` fija qué módulo es obligatorio, por par exacto o por centro (ver tabla de entidades arriba). `AsignacionesService.recalcular(usuarioId)` es el motor: toma los pares ACTIVOS de la vinculación, arma la unión de módulos requeridos por las reglas vigentes que matchean algún par **más** las reglas de centro de los centros donde tiene algún par activo, y la compara contra las `Asignacion` vigentes actuales — crea las `AUTOMATICA` que faltan y revoca las `AUTOMATICA` que ya no corresponden a ningún par activo. Es síncrono e idempotente, y **nunca toca las `MANUAL`** (las que carga un admin a mano). **Se auto-invoca** desde `UsuariosService` (`recalcularEnTx`, dentro de la misma transacción que cambió los pares) — ya no es solo un endpoint aparte, aunque `POST /asignaciones/recalcular/:usuarioId` se mantiene para recalcular a demanda. Los guards exactos, incluido **qué NO lo dispara**, están más abajo en "Backend (Asignaciones automáticas por par)". El registro de aprobaciones **ya existe** (Sprint 8): `AsignacionesService.modulosAprobados()` consulta las `Sesion` con `aprobada: true` y sale por `moduloVersion.moduloId`, así que aprobar **cualquier** versión cubre el módulo y una recontratación no obliga a rendir de nuevo lo ya aprobado — **mientras esa aprobación no haya vencido** (Story 8: el vencimiento se deriva de `Modulo.vigenciaMeses`, ver [decisiones/asignaciones.md](docs/decisiones/asignaciones.md)).

**Convención: `onDelete` explícito en relaciones Prisma opcionales.** El default para una relación `?` es `SetNull` y no siempre es seguro, así que toda relación opcional nueva tiene que decidir su `onDelete` a propósito — y verificarlo en el SQL de la migración, porque cuando es el default no se lee en el `.prisma`. El porqué y el caso que lo puso en evidencia (`ReglaAsignacion.puesto`, que con el default habría convertido una regla de par en una de centro al borrar un `Puesto`) están en [`docs/decisiones/infraestructura.md`](docs/decisiones/infraestructura.md).

**Unicidad de `ReglaAsignacion`: DOS índices parciales y ningún `@@unique`.** La tabla **no declara unicidad en el schema**: las dos que tiene viven sólo en el SQL de la migración `20260729171533_reglas_asignacion_soft_delete`, porque Prisma no expresa `WHERE` en `@@unique`.

```sql
-- (a) reglas CON puesto: en Postgres NULL nunca es igual a NULL, así que este
--     índice no cubre las de centro (cada fila con puesto_id NULL es distinta).
CREATE UNIQUE INDEX "reglas_asignacion_par_modulo_vivas"
  ON "reglas_asignacion"("puesto_id", "centro_costo_id", "modulo_id")
  WHERE "deleted_at" IS NULL;

-- (b) reglas de CENTRO, las que se le escapan al de arriba.
CREATE UNIQUE INDEX "reglas_asignacion_centro_modulo_sin_puesto"
  ON "reglas_asignacion"("centro_costo_id", "modulo_id")
  WHERE "puesto_id" IS NULL AND "deleted_at" IS NULL;
```

Los dos predicados son **ortogonales**: `puesto_id` elige qué alcance gobierna el índice, `deleted_at` elige qué filas están vivas — por eso se combinan en vez de unificarse. Con estos dos ya son cuatro los índices parciales invisibles para Prisma del proyecto (los otros: `Asignacion` con `WHERE revocada_at IS NULL`, y el `principal` de `VinculacionPuestoCentro`), y con el `WHERE nivel_id IS NULL` de `ModuloVersionCriterio` (Sprint 7) son **cinco** — misma advertencia: un `db push` sobre una base limpia los deja afuera. La lista completa y verificada está en `docs/pendientes.md`.

Corolarios en el service: `create()` busca con `findFirst` y `puestoId: dto.puestoId ?? null`, no con `findUnique` (que no puede consultar por NULL). El `?? null` es load-bearing — con `undefined` Prisma dropea la condición y terminaría reactivando cualquier regla de ese centro+módulo. Y busca **primero la viva y sólo después la eliminada**: como los índices sólo prohíben dos *vivas*, una viva y una eliminada del mismo triple pueden coexistir (se llega ahí moviendo una regla viva al módulo de una eliminada, porque la detección de colisión ignora las eliminadas), y una búsqueda sin ordenar podía agarrar la eliminada, revivirla y chocar contra la viva.

### Dashboard (Panel Principal)

**100% backend** (sin mock). Es el panel de la **plataforma**, y por eso **no repite lo que responde el Resumen de SIMA CHECK**: acá van las organizaciones, la gente y qué productos existen; cómo viene la capacitación se ve entrando al producto. Tres bloques:

- **KPIs**: Clientes y Subcontratistas (`GET /organizaciones` por `tipo`, sólo activas), Personas en el sistema (`habilitacion.total` de `GET /resumen/sima-check`) y Módulos activos (`GET /modulos` + `estadoModulo`). **Se fueron "Asignaciones pendientes/completadas"**: salían de un mock con estados que **no existen** en el modelo real, y además eran justo lo que contradecía al Resumen.
- **Estado del sistema**: lista **sólo lo que se chequea de verdad** — API (que el request haya salido) y Base de datos (el campo `db` de `GET /health`, que corre un `SELECT 1`). La versión anterior tenía además "Servicios de plataforma" e "Integraciones externas", que no consultaban nada: la segunda decía ADVERTENCIA fija, o sea que mostraba un problema inventado. Un panel que nunca puede dar mala noticia da **confianza falsa**, que es peor que no tenerlo.
- **Product cards**: SIMA CHECK (con tres números reales de adelanto —módulos, personas alcanzadas y **no habilitados en rojo**— sacados del **mismo** endpoint que el Resumen, así que no pueden divergir) + SIMA INSPECTIONS y SIMA AUDITS (roadmap, con ETA).

**Se eliminó "Actividad reciente"**, que era una tabla con nombres y fechas inventados a mano. Una de verdad necesita un registro de eventos que hoy no existe (`AuditLog` sólo cubre `Vinculacion` y sus pares) — anotado en `docs/pendientes.md`.

Los cuatro requests van con **`Promise.allSettled`, no `all`**: el estado del sistema es justamente lo que interesa cuando algo falló, así que un backend caído tiene que poder pintarse como "caído" en vez de tumbar la pantalla entera.

**"Editar módulos" es por ALCANCE, no por fila, y reusa el modal del alta.** El alta siempre trabajó por alcance (centro + puestos × módulos), así que editar fila por fila era una asimetría: el mismo concepto se cargaba de una forma y se editaba de otra, y agregarle un módulo a un puesto ya configurado obligaba a volver a "+ Nueva regla" y reelegir centro y puesto. Es también el motivo por el que el listado agrupa por alcance (ver arriba): con la tabla plana el botón aparecía repetido en cada fila del mismo puesto. Ahora "Editar módulos" abre el **mismo** `Modal` con `mode: 'edit'`: el centro y el alcance quedan fijos (se muestran como contexto, no como controles deshabilitados — mover una regla de lugar sigue siendo eliminarla y crear otra) y el multi-select de Módulos arranca con los ya configurados de ese alcance tildados. **Se guarda por diff**: tildar → `POST` (crea o revive), destildar → `DELETE`. Dos detalles que importan:
- **El multi-select gobierna existencia, no el eje `activo`.** Una regla desactivada aparece tildada con el sufijo "· configurada (desactivada)" para que destildarla —que la **elimina**— no sea una sorpresa; dejarla tildada no la reactiva (para eso está el botón de fila). Los módulos dados de baja del catálogo que ese alcance ya tenga configurados también se agregan a las opciones, para no ofrecer destildarlos a ciegas.
- **El diff se previsualiza antes de aplicar** ("se agregan X · se eliminan Y") y, si hay eliminaciones, se listan por nombre con la misma advertencia del modal de Eliminar. Guardar está deshabilitado sin cambios; vaciar el set **sí** es válido (equivale a eliminar todas las reglas de ese alcance).

**Por qué el diff y no `PATCH { moduloId }`:** cambiar el módulo en el lugar conserva el `id` y el `createdAt` de la fila, así que la regla queda diciendo que **siempre** obligó al módulo nuevo — y aunque el AuditLog ya existe (Story 9), hoy no cubre `ReglaAsignacion`, así que el módulo anterior no queda registrado en ningún lado. Alta + baja deja los dos hechos (la vieja con su `deletedAt`, la nueva con su `createdAt`). El endpoint `PATCH /reglas-asignacion/:id { moduloId }` existe y está testeado, pero **esta pantalla no lo usa**: queda disponible para cuando el AuditLog cubra esta entidad. Lo único que el frontend manda por `PATCH` es `{ activo }`. Después de cada mutación, **banner indigo** sobre el acordeón con el resumen del recálculo (`{usuarios, creadas, revocadas}`) — la consecuencia no se ve en el listado, lo que cambia son las asignaciones de otras personas. **El alta es secuencial, no `Promise.allSettled`**: cada POST abre ahora una transacción que recalcula todo el centro, y los N triples de una tanda comparten centro, así que mandarlos en paralelo eran N transacciones peleando por las mismas filas de `asignaciones`. Al acumular el resumen de la tanda, `usuarios` se combina con **máximo y no con suma** (es la misma gente en cada respuesta) — supuesto que hoy garantiza el modal con su `<select>` único de centro; si algún día se permite multi-centro por tanda, el máximo subcuenta y no hay arreglo del lado del cliente, porque la API devuelve un conteo y no los ids |
| Asignaciones | `training-assignments` | **100% backend** (sin mock), y **pantalla de CONSULTA por persona, no de acción** — el modelo real cambió el sentido de la pantalla: las asignaciones ya no se cargan una por una, las deriva el motor desde las `ReglaAsignacion` y los pares de cada persona; lo que aporta la pantalla es *"¿qué le corresponde a esta persona y por qué?"*. Es **por persona y no una tabla global** por un límite duro de la API: `GET /asignaciones` **exige** `?usuarioId=` y no existe endpoint que liste las de todo el mundo (construirla iterando sobre todos los usuarios serían N requests). Flujo: buscador por nombre o DNI contra `GET /usuarios` (tope 20 resultados) con estado vacío e instrucción mientras no haya nadie elegido → elegida la persona, **contexto** arriba (rol, organización, DNI) con los chips de sus **pares activos**, que son la causa de las automáticas; si no tiene ninguno se dice explícito ("sin pares activos — no le corresponde ninguna capacitación automática": es una cardinalidad válida y explica la ausencia). Después, tabla de **vigentes** (módulo · badge de origen **Automática** indigo / **Manual** slate · columna **"Por qué"**) con **"Revocar"** por fila (`PATCH /:id/revocar`, con confirmación), y las **revocadas** en una sección **colapsable** aparte con la fecha de revocación — no compiten visualmente con las vigentes pero están, porque el historial importa para ISO 9001. Botón **"Recalcular"** (`POST /asignaciones/recalcular/:usuarioId`, muestra `{creadas, revocadas}`): **dejó de ser parte del flujo normal** — los dos caminos que importan ya recalculan solos (tocar los pares de una persona y tocar una regla de su centro), así que el copy lo reformula como reconciliación manual "por si algo cambió por fuera de esos dos caminos". Ojo que **no** cubre dar de baja un Puesto/CentroCosto del catálogo: ahí no cambia nada, porque el motor no mira `Puesto.activo` (ver la sección del motor más abajo). **"+ Asignar manual"** se mantiene pero como excepción explícita: el modal avisa que una asignación MANUAL **no la toca el motor** (no se revoca sola si ningún par la pide) y traduce el 409 a un mensaje claro. Módulos sin versión publicada llevan el sufijo "(sin versión publicada)", mismo criterio que Reglas |

La barra de tabs y el breadcrumb `SIMA TRAINING › SIMA CHECK › {tab}` se renderizan en `BackofficeLayout.jsx` usando `SIMA_CHECK_PAGES` (Set) y `SIMA_CHECK_TABS` (array).

### Administración (Core)

- **Clientes** — tabla + modal crear/editar + toggle activo/inactivo
- **Puestos** — **100% backend**. Tabla + modal crear/editar + Desactivar/Activar (baja lógica), más un **buscador por nombre**. El buscador filtra **en memoria y no contra la API**: `GET /puestos` no acepta ningún `?q=` y el catálogo entero ya está cargado igual (hace falta completo para el contador y para poder seguir nombrando un puesto dado de baja), así que con 90 filas un request por tecla sería trabajo de más para el mismo resultado. Normaliza **sin acentos** — el catálogo real está lleno (Albañil, Cañista, Mecánico, Topografía) y nadie los tipea al buscar; es una copia de la de `SearchableSelect` a propósito, porque `components/` es un kit de UI que hoy **no importa nada de la app** y esa independencia vale más que ahorrar tres líneas. Con búsqueda activa el contador pasa a "X de Y puestos", porque decir "3 puestos registrados" sería mentira. **Centros de Costo** es la misma pantalla sin buscador: con 16 filas no hace falta
- **Usuarios** — **100% backend, ya migrado al modelo de vinculación**: lee y escribe la forma anidada (`usuario.vinculacion.rol` / `.organizacion` / `.pares` / `.parPrincipal`), no los campos planos que el backend dejó de exponer. **El alta manual desde el backoffice está fijada a rol ALUMNO** (decisión de producto: la abstracción de roles del sistema todavía no está definida, y el único admin previsto —HSE— entra con `AUTH_USER`/`AUTH_PASSWORD` del `.env`, no es un `Usuario`). El form ya no tiene `<select>` de rol: al crear siempre manda `rol: 'ALUMNO'`; **al editar no manda `rol` en absoluto** (`UpdateVinculacionDto.rol` es opcional en el backend), así que el rol real de un usuario legacy con otro rol (ADMINISTRADOR/COORDINADOR/AUDITOR) nunca se pisa en silencio — se muestra como texto de solo lectura. El backend sigue soportando los cuatro roles y la matriz tipo-de-organización ↔ rol sin cambios; el frontend tiene una copia chica de esa matriz (`TIPOS_ORG_POR_ROL` en `Usuarios.jsx`, comentada como espejo de `matriz-rol-organizacion.ts`) para filtrar el `<select>` de Organización según el rol efectivo (ALUMNO al crear, el rol cargado al editar) y no ofrecer una combinación que el backend vaya a rechazar con 400 — ya no existe la opción "— Sin organización —" (`organizacionId` es `NOT NULL`). Si el filtro deja el select sin ninguna organización válida, se muestra un mensaje en vez de un `<select>` vacío y se deshabilita Guardar. Las tabs pasaron de rol (Todos/Alumnos/Operadores) a **tipo de organización** (Todas/SIMA/Subcontratistas/Clientes), que es lo que ahora condiciona qué se puede hacer desde el form; la tabla sigue mostrando el rol y la organización reales de cada usuario sin filtrar. Incluye la sección de pares puesto/centro (ver "ABM de pares" más arriba) e "Importar Excel". **"Importar Excel" también quedó fijado a ALUMNO** (mismo criterio que el alta manual): el Excel dejó de tener columnas `rol`/`empresa`/`email` — la organización se elige una sola vez en el modal, antes de subir el archivo, filtrada a los mismos tipos INTERNA/SUBCONTRATISTA que admiten ALUMNO; si no hay ninguna organización de ese tipo, el modal muestra el mismo aviso que el alta manual y no deja analizar el archivo. Desde que el import resuelve Puesto/Centro de Costo contra el catálogo real, el modal ganó un paso de revisión por fila con resolución por grupo (nueva/parecida/duplicada) antes de confirmar — ver "Import de usuarios" en Backend más abajo. **Ojo con `modal?.mode`, no `modal.mode`:** el JSX del bloque de Rol se evalúa siempre al renderizar la página, aunque el modal esté cerrado (`modal` arranca en `null`) — acceder a `modal.mode` sin optional chaining tumbaba toda la pantalla con un `TypeError` apenas se entraba a Usuarios, no solo al abrir el modal. Mismo patrón que el resto del componente: siempre `modal?.campo`.

  **La tabla separa Puesto y Centro de costo, y despliega los pares adicionales (Story 11).** Eran una sola columna ("Electricista · Depósito") que además mostraba **sólo el par principal** — y `principal` es únicamente display: la persona rinde los módulos de **todos** sus pares. Ahora son dos columnas con el par principal, y una fila con más de un par ofrece un chip **`+N`** que despliega los demás. Detalle que importa: **los pares adicionales van enteros en la celda de Puesto** (`Soldador · Taller`), con la celda de Centro de costo **vacía** en esas líneas — **no** se parten entre las dos columnas, porque un nombre de centro largo que envuelva a dos líneas desalinea las filas y la tabla vuelve a mentir sobre qué va con qué, que es justo lo que la story arregla. El principal es el único par que ocupa las dos columnas. Los pares con `activo: false` se muestran tachados (mismo tratamiento que `HistorialUsuario.jsx`), para no sugerir que se puede filtrar por ellos: el backend sólo matchea pares activos.

  **Tres filtros nuevos, y los resuelve el BACKEND** (`?puestoId=`/`?centroCostoId=`/`?organizacionId=`), no la memoria: en el cliente sólo está el par principal, así que filtrar acá daría un resultado distinto del real. Combinan con **AND** entre sí, con el buscador y con las tabs. Son tres `<select>` simples y **no `MultiSelectFilter`** — la API toma un id único por parámetro. Puesto y Centro ofrecen el **catálogo completo** con sufijo `' (inactivo)'` (mismo criterio que `ParesPuestoCentro.jsx`): un puesto dado de baja puede seguir teniendo gente asignada y hay que poder encontrarla. El de **Organización se acota al tipo de la tab activa**, y **cambiar de tab descarta la organización elegida si no es de ese tipo** — si no, el AND daría cero siempre; puesto y centro no dependen de la tab y se conservan. Botón **"Limpiar filtros"** (visible sólo si hay alguno activo; resetea también el buscador, no la tab). El fetch de usuarios vive en **un solo `useEffect`** con deps `[filtroOrganizacion, filtroPuesto, filtroCentro, reloadKey]` y su guarda `active` contra respuestas viejas; las mutaciones recargan incrementando `reloadKey` en vez de tener su propio fetch. **Los catálogos se cargan aparte, una sola vez** — salvo después del import de Excel, que **sí** los refresca porque crea puestos y centros nuevos.

  **El contador de arriba cambia de texto con filtros activos.** Sin filtros de servidor queda como siempre (`"3 usuarios — 3 en total"`); con alguno activo pasa a `"2 usuarios con los filtros aplicados"`, porque `usuarios` ya es el resultado filtrado y "en total" dejaría de ser el total real. Los contadores de las **tabs** sí quedan sobre el resultado filtrado, con la ambigüedad que eso implica (una tab en 0 no distingue "no hay de ese tipo" de "los filtros los excluyeron") — anotado en [`docs/pendientes.md`](docs/pendientes.md), no se arregla sin pedir los conteos aparte.

  **"Ver historial" por fila (Story 10)** abre `HistorialUsuario.jsx`, la **hoja de vida** de esa persona contra `GET /usuarios/:id/informe`: cabecera con identidad, rol, organización y sus pares; el **veredicto de habilitación** como bloque dominante; la tabla de capacitaciones asignadas con su estado de vencimiento; y tres secciones **plegadas por defecto** — revocadas, historial de rendiciones e historial de cambios (el audit log). El historial de rendiciones muestra **fecha y hora** de cada intento (columna "Fecha y hora", la hora en `font-mono` y sin segundos): varios intentos del mismo módulo caen el mismo día, y sin la hora tres filas idénticas en fecha no dicen en qué orden se rindieron ni cuánto pasó entre una y otra. Sale de `createdAt` (reloj del **servidor**) y no de `finalizadaEn` (reloj del dispositivo), mismo criterio con el que el backend calcula la vigencia. Arriba de todo, junto a "← Volver a Usuarios", un botón **"↻ Actualizar"** vuelve a pedir el informe completo sin salir de la pantalla (Story 6 del sprint 13-08): el caso es que alguien rinda en la tablet y el resultado no aparezca acá hasta salir y volver a entrar. **Refrescar no usa `loading` ni `error`** —los dos son early returns que reemplazan la pantalla entera, y para un refresco eso borraría el informe que se estaba leyendo—: tiene su propio par `refrescando`/`errorRefresco`, y un fallo se avisa en un banner arriba dejando abajo los últimos datos que sí llegaron. Detalle de las decisiones en "Backend (Story 10 — Informe de usuario)", más abajo. Dos cosas de esta pantalla que importan para no romperlas:
  - **La navegación es un early return DENTRO de `Usuarios.jsx`**, no una página propia de `App.jsx` (mismo patrón que la vista de contenido de `TrainingModules.jsx`). Es lo que hace que volver conserve la tab, la búsqueda y los usuarios ya cargados: el componente **nunca se desmonta**, así que sus `useState` siguen vivos y no hace falta levantar estado a ningún lado. Moverla a `App.jsx` sí lo desmontaría y volver resetearía los filtros — está comentado en el código. **Sigue siendo cierto ahora que la vista vive en la URL** (`#usuarios/historial/42`): ese hash y `#usuarios` son la misma *página* para `App.jsx`, que renderiza el mismo componente en los dos casos — lo único que cambia es el `sub`. `historialId` se **deriva** de ahí, no es un `useState`, así que un F5 estando en el historial de alguien vuelve a abrirlo y el botón "atrás" sale al listado.
  - **El audit log se renderiza como `campo: antes → después`, nunca JSON crudo**, y traduce a nombres los ids que el log guarda en bruto (`puestoId`/`centroCostoId` son UUID, `organizacionId` un entero) usando los catálogos que `Usuarios.jsx` **ya tiene en memoria** y le pasa por props — cero requests extra. Si un id no está en el catálogo (se borró del todo) cae al valor crudo en vez de romper. Se descartan los pares donde `antes === despues` (los CREATE traen `deletedAt: null → null`, ruido puro); el resto se muestra completo, que para eso es auditoría.

## App SIMA CHECK — flujo

Todas las pantallas son **tarjetas blancas** (`bg-white border border-slate-200 rounded-2xl shadow-2xl`) sobre un fondo claro con gradiente gris. Para usar imagen de fondo real, reemplazar el `background` inline en `App.jsx` por `backgroundImage: "url('/bg-industrial.jpg')"`.

El **logo** (`public/SIMA_CHECK-logo.png`) se renderiza en `App.jsx` encima de la card, visible en todas las pantallas.

1. **Ingreso por DNI** — campo numérico (`inputMode="numeric"`), botón INGRESAR, validaciones: vacío / DNI no encontrado
2. **Capacitaciones pendientes** — nombre y empresa de la persona + lo que devuelve `GET /tablet/pendientes`: sus asignaciones **vigentes sin aprobación**; lista vertical de botones (`red-600`) con ícono y título; estado vacío si no hay pendientes. Cada ítem viaja con su `reintentos`: si la persona agotó el tope o está dentro de la espera, el botón se pinta gris y **deshabilitado con el motivo debajo** ("Podés reintentar a partir del 14/08 a las 09:30"), pero **el módulo sigue listado** — la obligación no desapareció, sólo no se puede rendir todavía. Si hay tope declarado y quedan intentos, se avisa cuántos
3. **Evaluación** — las preguntas que declare la versión (`preguntasPorExamen`, 3 si no declara), sorteadas del pool; barra de progreso avanza **al responder** (no al llegar); tipos de pregunta:
   - `truefalse`: 2 botones V/F (verde/rojo)
   - `multiple`: lista vertical, selección en `slate-900`
   - `image-options`: grid 2×2 de imágenes, selección con borde `red-600` + ring
   - Campo opcional `imagen` en cualquier pregunta: muestra la imagen del enunciado encima de las opciones. Llega como `{ clave, url }` — `QuestionCard` muestra la `url` y manda la `clave` de vuelta, porque el backend corrige contra la clave cruda de storage
4. **Resultado** — score %, badge APROBADO / DESAPROBADO, botones: Mis capacitaciones / Volver al inicio, y **"Reintentar evaluación" sólo si DESAPROBÓ**. **El resultado lo calcula el backend**, no la app: el POST manda respuestas crudas y devuelve el veredicto — incluido el `reintentos` recalculado después de registrar la sesión, que es lo que decide si "Reintentar evaluación" se ofrece o se reemplaza por el motivo. Aprobado no se ofrece reintentar y **no es porque el backend lo rechace** —al contrario, el contador de intentos se resetea justo al aprobar, así que pasaría—: es que el módulo ya salió de pendientes (`pendientes()` filtra los `modulosAprobados`) y volver a rendirlo sólo sumaría sesiones al historial de la persona y le daría la chance de "desaprobar" algo que ya tenía aprobado

Al finalizar, el módulo deja de aparecer en pendientes **sólo si aprobó**. No hay ningún estado que cambie: la `Asignacion` sigue vigente y lo que pasa es que se completa su `moduloVersionId`, así que "pendiente" es *vigente sin aprobación* — ver [decisiones/sesiones.md](docs/decisiones/sesiones.md) y [decisiones/asignaciones.md](docs/decisiones/asignaciones.md). Si desaprueba, el módulo sigue en la lista y puede reintentar; cada intento es una `Sesion` nueva.

## Buscador en los desplegables largos (`SearchableSelect`)

Con el catálogo real —**88 puestos**, 16 centros de costo— un `<select>` nativo se elige scrolleando con el ojo. `SearchableSelect` (`components/SearchableSelect.jsx`) es el desplegable de selección **única** con buscador arriba; `MultiSelectFilter` sigue siendo el de selección múltiple, y son componentes **separados** a propósito (ver [decisiones/usuarios.md](docs/decisiones/usuarios.md)).

Se aplicó **sólo donde la lista es larga** — Puesto y Centro de costo, en los cuatro lugares donde aparecen: los filtros de Usuarios, `ParesPuestoCentro` (el form de carga de una persona), el resolver de `ImportUsuariosModal` y el modal de Reglas. Los desplegables cortos (base, nivel, organización, tipo de pregunta, respuesta correcta, la acción del import) **siguen siendo `<select>` nativos**: abrir un panel con buscador para elegir entre tres opciones agrega un paso en vez de sacarlo.

**El panel se renderiza en un portal a `document.body` con `position: fixed`**, y eso no es decoración: la mitad de los consumidores viven dentro de un `Modal`, cuyo cuerpo es `overflow-y-auto` — un panel `absolute` ahí adentro queda **recortado** por ese contenedor. El costo es que el panel se cierra ante cualquier scroll (listener en fase de captura, porque los eventos de scroll no burbujean y el que importa es el del cuerpo del modal).

`opcionesCatalogo()` (`core/format/catalogo.js`) adapta una fila de catálogo a `{ id, label }` y estampa el sufijo `" (inactivo)"` que Usuarios y `ParesPuestoCentro` ya venían repitiendo a mano.

## Decisiones de arquitectura

- No se usa react-router intencionalmente. **La navegación sí vive en el hash de la URL** (`#usuarios`, `#usuarios/historial/42`), vía `hooks/useNavigation.js` — pero eso no es un router: no hay rutas anidadas, ni params, ni `<Link>`, ni matching, ni dependencia nueva. Es el hash partido por `/`: el primer segmento es la página y el resto lo interpreta la pantalla. Ese resto (el `sub`) se usa para **dos cosas distintas**: una sub-vista que es un LUGAR (`#usuarios/historial/42`, con `setSub`, apila en el historial y sobrevive al F5) y una INTENCIÓN de entrada que la pantalla consume al montar (`#questions/base/<id>/nivel/<id>`, con `replaceSub`, no apila y se limpia sola). Ver [decisiones/navegacion.md](docs/decisiones/navegacion.md).
- No existe persistencia entre sesiones — todo es estado local en React, **salvo la página y el historial de una persona**, que viven en la URL. Los filtros y búsquedas de cada pantalla **sí** se pierden con un F5, a propósito. El editor de contenido de un módulo tampoco se restaura, y eso es deliberado: tiene cambios sin guardar en memoria, así que restaurar la vista sin ellos mentiría sobre lo que quedó.
- **Regla de dependencia**: `sima-check/` puede importar de `core/`. `core/` nunca importa de `sima-check/`. `Dashboard` puede importar de ambos. **Se cumple sin excepciones** — la última violación (`ImportPreguntasModal.jsx` importando `backendTypeBadge`) se cerró moviendo el helper a `core/format/`, sin dejar re-export puente. Cuando un helper lo necesitan las dos capas, la salida es siempre esa: **subirlo a `core/format/`**, no importar hacia abajo.
- El estado del flujo de la app tablet (persona, pendiente elegido, examen, respuestas, resultado) se eleva a `App.jsx`: las pantallas son de presentación y no piden datos por su cuenta. Es también el motivo por el que una recarga a mitad de rendir pierde la evaluación, y por el que el banner de actualización no se muestra durante la evaluación (ver [decisiones/tablet.md](docs/decisiones/tablet.md)).
- Los modales manejan estado local.
- Los gráficos son SVG puro (sin librerías).
- Tailwind v3 es obligatorio.
- **Los dos frontends nombran la entidad `usuario`, no `employee`** — alineado con el `Usuario` del backend, que unifica `User` + `Employee` (ver arriba). En la **app tablet** alcanza a `pages/UsuarioSelection.jsx` y al prop que se pasa entre pantallas (`usuario`); en el **backoffice** alcanzaba a `usuarios-mock.js`, `training-assignments.js` y `evaluations.js`, los tres ya eliminados al migrar sus pantallas. Los duplicados del modelo viejo (los `employees.js` de los dos frontends y `EmployeeSelection.jsx`) se eliminaron; quedan en el historial de git. `User` (`core/data/users.js`) **no** entra en este rename: son las cuentas del backoffice (administrador/coordinador), otra cosa.
- La navegación de SIMA CHECK en el backoffice usa un Set (`SIMA_CHECK_PAGES`) en `BackofficeLayout.jsx` para detectar cuándo renderizar la barra de tabs y el breadcrumb de dos niveles.
- La pantalla Preguntas maneja su propia navegación interna (`selectedModuleId`) con `useState` — no requiere cambios en el router global.
- Las imágenes le llegan a la app tablet como `{ clave, url }`: muestra la `url` y manda la `clave` de vuelta como respuesta, porque el backend corrige contra la clave cruda de storage. Las rutas relativas a `public/` (ej. `/images/cartel.png`) sobreviven sólo como formato legacy del import de Excel.
- El tipo `image-options` usa las mismas rutas en `options[]` y `correctAnswer` — la comparación de respuesta correcta es por igualdad de string (misma ruta).

## Decisiones de diseño — [`docs/decisiones/`](docs/decisiones/)

**El porqué de cada decisión de diseño vive en `docs/decisiones/`, un archivo por dominio.** Este archivo describe el **estado actual** (entidades, endpoints, módulos, pantallas, convenciones); allá está por qué está armado así, qué alternativas se descartaron y qué costos se aceptaron.

Están organizadas **por dominio y no por sprint**: el orden cronológico sólo le sirve a quien vivió los sprints, y alguien que abre `asignaciones.service.ts` quiere el porqué de ese archivo, no un recorrido por ocho sprints. Cada archivo incluye también el frontend de su dominio — la división es por tema, no por capa.

## Cómo agregar un producto futuro (ej: SIMA INSPECTIONS)

1. Crear `src/sima-inspections/data/` con sus entidades.
2. Crear `src/sima-inspections/pages/` con sus pantallas (incluyendo un `Overview.jsx`).
3. Agregar el producto al sidebar en `BackofficeLayout.jsx`:
   - Nuevo ítem en la sección "Productos"
   - Nuevo Set equivalente a `SIMA_CHECK_PAGES` y array de tabs
4. Registrar las páginas nuevas en `PAGES` de `App.jsx`.
5. Agregar una product card en `Dashboard.jsx`.

No hay excepciones a esta convención: `ReglasAsignacion.jsx` era la única (vivía en `core/pages/` siendo un tab de SIMA CHECK) y ya se movió a `sima-check/pages/`.
